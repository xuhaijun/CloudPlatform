车路通 DSSAD 云平台 —— 服务启停与状态检测命令集

源文件 docs/devops/服务启停与状态检测命令集.md 由 scripts/md2html.py 生成

文档目的：把「前后端服务的启动 / 停止 / 状态检测 / 依赖与运维」会用到的所有命令整理成一份带注释的手册。 每条命令给出两种写法：

  1. 脚本封装形式（推荐，已处理 JDK 版本探测、代理绕过、路径转换等坑）；
  2. 底层真命令形式（脚本不可用、或想精确控制时直接敲）。

文中所有示例默认在仓库根目录 CloudPlatform/ 下执行。

0. 先选对工具（角色一览）#

你的目标 用什么 备注
本地改代码 / 联调热重启 dev.sh 跑 classes 目录、支持热重启
上线前「验产物」终验 build.sh + run-local.sh 跑打好的 jar
判断服务是否健康 health.sh / mqtt-watch.sh 全链路冒烟 / 通道探针
起 MySQL / Redis / MQTT 依赖 docker compose 仅依赖，应用另起
数据库备份 backup.sh 一致性备份 + 校验 + 轮转
生产容器编排 docker compose -f docker-compose.prod.yml Nginx 唯一入口
生产主机部署 systemd 单元 jar + systemd，非容器

默认端口约定（可用环境变量覆盖）：

端口 用途
8080 后端（覆盖：APP_PORT=18080 ...）
5173 前端 Vite dev server（覆盖：WEB_PORT=5174 ...）
3306 MySQL
6379 Redis
1883 MQTT Broker

两条贯穿全局的铁律（对应真实踩坑）：

# ① 回环地址一律绕过代理：本机注入了 http_proxy，连 127.0.0.1 也会被转发返回 502，
#    极易误判成「服务没起来」。
curl --noproxy '*' ...

# ② JDK 必须 21+；Windows 上 Maven 必须用 mvn.cmd（否则报「找不到主类 Launcher」）。
mvn.cmd ...   # 不是 mvn

1. 环境自检#

# 检查 JDK21 / Maven / Node / Docker、项目结构、端口占用、prod 必填变量
bash scripts/check-env.sh

# 生成一个 24 字节十六进制强随机口令（填 .env 用，避免弱口令）
bash scripts/check-env.sh --gen-secret 24

底层等效（想手动确认某一项时）：

node -v          # 必须 ≥ v18（Vite 6 要求）
npm -v
java -version    # 必须 21
mvn -version
docker info      # 守护进程是否就绪（CLI 装了但没启动会失败）

2. 构建（出产物）#

# 后端打包：走 mvn verify（含 227 个测试 + JaCoCo 覆盖率门槛 0.60，不达标即失败）
bash scripts/build.sh

# 后端 + 前端一起构建（前端会 npm ci + vue-tsc 类型检查 + vite build）
bash scripts/build.sh --web

# 跳过测试（仅本地快速试跑，**产物不可用于发布**）
bash scripts/build.sh --skip-tests

# 额外构建容器镜像（需要 Docker 守护进程）
bash scripts/build.sh --docker

# 先 clean 再构建
bash scripts/build.sh --clean

# 组合：全量（前端 + 镜像）
bash scripts/build.sh --web --docker

底层等效：

# —— 后端 ——
cd cloud-platform-server
mvn.cmd -B verify                 # Windows 用 mvn.cmd；Linux/macOS 用 mvn
mvn.cmd -B package -DskipTests    # 跳过测试时的等价目标

# —— 前端 ——
cd cloud-platform-web
npm ci                            # 按 lockfile 精确安装（首次/CI 用）
npm install                       # 开发机增量安装
npm run type-check                # vue-tsc 零错误门禁
npm run build                     # 产出 dist/

# —— 容器镜像 ——（必须在仓库根目录，构建上下文为仓库根）
docker build -t dssad-cloud-platform:local .

产物位置：

后端  cloud-platform-server/target/dssad-cloud-platform.jar
前端  cloud-platform-web/dist/
镜像  dssad-cloud-platform:local

3. 本地开发启动（dev.sh）#

面向「改代码」：跑 classes 目录、支持热重启。

bash scripts/dev.sh            # 起后端(8080)+前端(5173)，后台就绪后返回
bash scripts/dev.sh --api     # 只起后端
bash scripts/dev.sh --web     # 只起前端（后端需已在跑）
bash scripts/dev.sh --stop    # 停止本脚本启动的全部进程
bash scripts/dev.sh --logs    # tail -f 跟随两个日志（Ctrl+C 退出）

底层等效：

# —— 后端：spring-boot:run，local profile（H2 文件库 + MQTT 关闭 + 模拟器开启）——
cd cloud-platform-server
env -u SERVER__PORT -u PORT -u http_proxy -u https_proxy \
    mvn.cmd -B spring-boot:run \
    -Dspring-boot.run.profiles=local \
    -Dspring-boot.run.arguments="--server.port=8080"

# —— 前端：Vite dev server，/api 已代理到 8080 ——
cd cloud-platform-web
npm run dev

停止的底层逻辑（脚本已封装，手动兜底见第 9 节）：先 kill -TERM 进程组 → 等 3s → kill -9。

4. 成品 jar 启动（run-local.sh）#

面向「验产物」：跑打好的 jar，能提前暴露「开发能跑、打的包起不来」类问题。

bash scripts/run-local.sh                 # 前台，local profile（H2 零外部依赖）
bash scripts/run-local.sh --bg            # 后台，轮询健康接口到 200 后返回
bash scripts/run-local.sh --stop          # 优雅停止（SIGTERM → 等 15s → SIGKILL）
bash scripts/run-local.sh --prod          # prod profile（需 .env + MySQL/Redis/Broker 就绪）
bash scripts/run-local.sh --port 18080   # 换端口（端口冲突时）

底层等效：

JAVA_OPTS="-Xms256m -Xmx1g -XX:+UseG1GC -Dfile.encoding=UTF-8 -Duser.timezone=Asia/Shanghai"

# local profile：H2 文件库，零外部依赖；清掉外部注入的 SERVER__PORT / 代理变量
env -u SERVER__PORT -u PORT -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY \
  java $JAVA_OPTS -jar cloud-platform-server/target/dssad-cloud-platform.jar \
  --spring.profiles.active=local --server.port=8080

# prod profile：读仓库根 .env，需要真实 MySQL/Redis/MQTT
env -u SERVER__PORT -u PORT -u http_proxy -u https_proxy \
  java $JAVA_OPTS -jar cloud-platform-server/target/dssad-cloud-platform.jar \
  --spring.profiles.active=prod --server.port=8080

⚠️ local profile 下令牌存于内存 StateStore，重启后登录态丢失（设计如此），重新登录即可；多实例共享登录态需开 Redis（dssad.redis.enabled=true）。

5. 状态检测 / 探活#

5.1 公开健康检查（无需令牌）#

# 编排/探活用这个：返回 {"code":"0000",...} 即存活
curl --noproxy '*' -s http://127.0.0.1:8080/api/v1/monitor/health-check

5.2 全链路冒烟（health.sh）#

不只探活，而是逐条断言「能写、能读、鉴权有效、登出真失效」。

bash scripts/health.sh                                       # 默认 http://127.0.0.1:8080
bash scripts/health.sh --base-url http://127.0.0.1:18080     # 自定义地址
bash scripts/health.sh --user admin --password 'dssad@2026'  # 自定义账号
bash scripts/health.sh --no-simulator                        # 生产态：跳过「注入事故场景」断言

底层断言（节选，手动验证时用）：

# ① 无令牌访问受保护接口 → 必须被拒（code 2001）
curl --noproxy '*' -s "http://127.0.0.1:8080/api/v1/vehicles?page=1&size=1"

# ② 登录拿令牌（从响应里抠 token 字段）
TOKEN=$(curl --noproxy '*' -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"dssad@2026"}' \
  http://127.0.0.1:8080/api/v1/auth/login \
  | grep -o '"token":"[^"]*"' | cut -d'"' -f4)
echo "$TOKEN"

# ③ 带令牌访问监控/看板接口
curl --noproxy '*' -s -H "X-Token: $TOKEN" http://127.0.0.1:8080/api/v1/monitor/cache
curl --noproxy '*' -s -H "X-Token: $TOKEN" http://127.0.0.1:8080/api/v1/monitor/mqtt
curl --noproxy '*' -s -H "X-Token: $TOKEN" http://127.0.0.1:8080/api/v1/dashboard/overview

# ④ 登出后旧令牌必须失效（服务端真吊销，非前端自欺）
curl --noproxy '*' -s -X POST -H "X-Token: $TOKEN" http://127.0.0.1:8080/api/v1/auth/logout
curl --noproxy '*' -s -H "X-Token: $TOKEN" "http://127.0.0.1:8080/api/v1/vehicles?page=1&size=1"
#   ↑ 期望返回 code 2001

5.3 MQTT 通道探针（mqtt-watch.sh）#

专治「探活全绿但收不到数据」：平台 health-check 在 Broker 断开时仍返回成功（刻意设计）， 所以通道健康要看专用端点 /api/v1/monitor/mqtt-health（DOWN 时返回 HTTP 503）。

bash scripts/mqtt-watch.sh                          # 默认 8080
bash scripts/mqtt-watch.sh --base-url http://10.0.0.5:8080
bash scripts/mqtt-watch.sh --deep                   # 登录读积压/丢弃指标
bash scripts/mqtt-watch.sh --allow-disabled         # 本地未启用视为正常
bash scripts/mqtt-watch.sh --quiet                  # 只输出一行机器可读结果

底层等效：

# 200 = UP/DISABLED；503 = DOWN；看 JSON 里的 status / state / reason 字段
curl --noproxy '*' -s -w '%{http_code}' -o /dev/null \
  http://127.0.0.1:8080/api/v1/monitor/mqtt-health

退出码分级（可直接接 cron / Zabbix 告警）：

0  正常
10 通道未启用（生产态属配置错误）
20 通道未连通（DOWN / RECONNECTING / 凭据致命错误）
30 队列积压超阈值（链路通但消费不过来）
40 已发生丢弃（最严重，数据不可恢复）
90 探针侧问题（端点不可达 / 404=实例版本过旧 / 鉴权失败）

6. 数据库与外部依赖（docker compose）#

应用本身不进 docker-compose.yml（开发需要热重启），这里只起依赖。

docker compose up -d                          # MySQL 8.4 + Redis 7（首次自动执行建表脚本）
docker compose --profile mqtt up -d           # 额外起 Mosquitto（联调 MQTT 时）
docker compose ps                             # 查看状态
docker compose logs -f mysql                 # 跟随某服务日志
docker compose down                          # 停止（保留数据卷）
docker compose down -v                       # 停止并清空数据（重置环境）

# 把应用切到「真依赖」模式（替代 dev.sh 的 local profile）
mvn.cmd spring-boot:run -Dspring-boot.run.profiles=prod -Dspring-boot.run.arguments="--server.port=8080"
# 或：bash scripts/run-local.sh --prod

手动建表 / 迁移（首次或改 DDL 后，需人工对照手写脚本）：

# 用容器里的库或本地库执行生产建表脚本
mysql -h127.0.0.1 -uroot -p dssad_cloud \
  < cloud-platform-server/db/schema-mysql.sql

7. 备份与恢复演练（backup.sh）#

bash scripts/backup.sh                                       # 默认 .env + 默认参数
bash scripts/backup.sh --out /data/backups --keep 30        # 指定输出目录与保留份数
bash scripts/backup.sh --restore-check                      # 额外做真恢复演练（建临时库→比对表数→删除）
bash scripts/backup.sh --dry-run                            # 预演，不写任何文件
bash scripts/backup.sh --db dssad_cloud --env-file /etc/dssad/db.env

底层等效（mysqldump 真命令，脚本已加 --single-transaction 等参数防坑）：

MYSQL_PWD="$DB_PASSWORD" mysqldump \
  --host="$DB_HOST" --port="$DB_PORT" --user="$DB_USERNAME" --protocol=TCP \
  --single-transaction --quick --routines --triggers --events \
  --default-character-set=utf8mb4 --hex-blob --set-gtid-purged=OFF \
  --source-data=2 "$DB_NAME" | gzip -9 > dssad_cloud_$(date +%Y%m%d_%H%M%S).sql.gz

退出码分级：0 成功 / 10 用法错 / 20 连接失败 / 30 dump 失败 / 40 校验失败 / 45 恢复演练失败 / 50 轮转失败 / 60 客户端缺失。

8. 生产部署#

8.1 容器编排（docker-compose.prod.yml）#

# ① 先填好 .env（可参考 deploy/systemd/dssad-cloud-platform.env.example）
cp deploy/systemd/dssad-cloud-platform.env.example .env
#   ⚠️ 真实 .env 绝不能提交（.gitignore 已排除 .env）

# ② 前端静态产物需先在构建机产出（compose 只挂载，不构建）
bash scripts/build.sh --web

# ③ 拉起整套（Nginx 唯一入口 + 应用 + MySQL + Redis）
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml ps

单独跑镜像（不走 compose 时）：

docker run --rm -p 8080:8080 \
  -e SPRING_PROFILES_ACTIVE=prod \
  -e DB_HOST=host.docker.internal -e DB_USERNAME=dssad -e DB_PASSWORD='***' \
  -e DSSAD_ENTERPRISE_ID=DSSAD-ENT-0001 \
  -e DSSAD_MQTT_BROKER_URL=tcp://broker:1883 \
  -e DSSAD_REGULATORY_BASE_URL=https://reg.example.com \
  -e DSSAD_STORAGE_PUBLIC_URL=https://dssad.example.com/media \
  -e DSSAD_SRS_URL=https://dssad.example.com \
  dssad-cloud-platform:local

8.2 systemd 主机部署（jar + systemd，非容器）#

# ① 建系统用户与目录
sudo useradd --system --no-create-home --shell /usr/sbin/nologin dssad
sudo mkdir -p /opt/dssad /etc/dssad /var/log/dssad /data/dssad/media

# ② 部署 jar 与环境变量文件（含明文口令，权限必须 600）
sudo cp cloud-platform-server/target/dssad-cloud-platform.jar /opt/dssad/
sudo cp deploy/systemd/dssad-cloud-platform.env.example /etc/dssad/dssad-cloud-platform.env
sudo chmod 600 /etc/dssad/dssad-cloud-platform.env
sudo chown -R dssad:dssad /opt/dssad /var/log/dssad /data/dssad

# ③ 安装并启用服务（⚠️ 该 .service 文件必须是 LF 换行，否则 systemd 报 Invalid argument）
sudo cp deploy/systemd/dssad-cloud-platform.service /etc/systemd/system/
sudo systemctl daemon-reload

# ④ 启动 + 开机自启
sudo systemctl enable --now dssad-cloud-platform

# ⑤ 状态与日志
systemctl status dssad-cloud-platform
journalctl -u dssad-cloud-platform -f

# ⑥ 停止 / 重启
sudo systemctl stop dssad-cloud-platform
sudo systemctl restart dssad-cloud-platform

systemd 单元已配优雅停机（KillSignal=SIGTERM + TimeoutStopSec=60），重启不会丢在途报文。

9. 排障速查命令#

# —— 端口占用（不依赖 netstat/ss/lsof，用 bash 内建 /dev/tcp）——
( exec 3<>/dev/tcp/127.0.0.1/8080 ) 2>/dev/null && echo "8080 占用" || echo "8080 空闲"

# Windows 版（看 PID 后用 taskkill 收掉）
netstat -ano | findstr :8080

# —— 进程是否还活着 ——
kill -0 <pid> 2>/dev/null && echo alive || echo dead

# —— 列出 java 进程（确认 jar 是否起来）——
jps -l | grep dssad

# —— 跟随日志 ——
tail -n 50 -f .run/app-8080.log       # run-local.sh 后台日志
tail -n 30 -f .run/dev-api.log        # dev.sh 后端日志
tail -n 20 -f .run/dev-web.log        # dev.sh 前端日志

# —— 手动停止（脚本已封装，以下是兜底）——
kill -TERM <pid>     # 优雅：让 Spring shutdown hook 执行完
sleep 3
kill -9  <pid>       # 强制：优雅超时才用

# —— H2 控制台（local profile 才能用）——
#   浏览器打开 http://127.0.0.1:8080/h2-console ，JDBC URL 见 application-local.yml

# —— 看应用真实 JVM ——
java -XshowSettings:properties -version 2>&1 | grep 'java.home'

11. 源码管理与双远程推送（git）#

本项目配置了两个远程：origin = Gitee（国内主仓）、github = GitHub（镜像仓）。 一次提交需两个远端都推，避免两端代码不一致。

# —— 查看 / 新增远程 ——
git remote -v                                                    # 列出已配置远程（当前：origin=gitee, github=github）
git remote add origin  git@gitee.com:ecloudy/cloud-platform.git   # 若缺则补
git remote add github  git@github.com:xuhaijun/CloudPlatform.git  # 若缺则补

# —— 工作区与分支状态 ——
git status -sb                     # 分支 + 未跟踪/修改（简洁）
git branch -vv                     # 各分支跟踪的远端（当前 main 跟踪 github/main）
git fetch --all                    # 拉取所有远端最新引用（不合并）

# —— 暂存与提交（提交信息遵循 Conventional Commits）——
git add -A                         # 暂存全部改动（也可精确指定文件，避免误提交 .env）
git commit -m "feat: 接入下行发布限流并补齐监控计数"

# —— 推送到双远程（推荐显式两行，防止漏推）——
git push origin main               # ① 推 Gitee 主仓
git push github main               # ② 推 GitHub 镜像
#   等价一行写法（任一侧失败立即中断，不会只推一半）：
git push origin main && git push github main

# —— 首次推送某分支并设置上游跟踪 ——
git push -u origin main            # 之后 git push 默认推 origin（本项目 github 已设 tracking）

# —— 拉取 / 合并远端改动 ——
git pull github main               # 从 GitHub 拉并合并
git pull origin main               # 从 Gitee 拉并合并

# —— 查看历史 ——
git log --oneline -20              # 最近 20 条
git log --graph --oneline --all    # 全部分支图谱

双推注意事项：

  • SSH 密钥需同时授权 Gitee 与 GitHub（ssh -T git@gitee.com / ssh -T git@github.com 验证连通性）。
  • 本机注入了 http_proxy：推 Gitee/GitHub 走 SSH（端口 22）不受影响；若改用 HTTPS 远程，需对这两个域名在 ~/.ssh/config 或 git 配置里设 http.proxy = ""，否则会被代理转发失败。
  • 提交前确认 .env、密钥文件未被 git add（.gitignore 已排除 .env；用 git status 复核）。
  • 推送失败多半是 SSH key 未授权或网络被代理拦截，先用 ssh -T 隔离排查，再回头推。
