1. 背景：政策与行业驱动#

1.1 监管侧的刚性需求#

智能网联汽车（尤其低速自动驾驶：环卫、物流配送、园区接驳、矿山等封闭/半封闭场景） 在准入与上路试点中普遍被要求具备：

要求 来源 对本产品的意义
自动驾驶数据存储系统（DSSAD） GB 汽车数据安全系列标准、准入试点通知 车端记录能力，本产品是云端延伸
事故后数据取证与回传 各地智能网联汽车管理条例 事故取证链路是本产品的核心卖点
车辆运行状态上传监管平台 准入试点运行管理要求 云云对接（MQTT + HMAC）是准入的硬门槛
远程接管能力与接管记录 示范应用管理规范 远驾接管台账属于强监管数据

结论：这不是「锦上添花」的增值功能市场，而是合规准入的必备件市场—— 不接入就上不了牌、拿不到示范应用资质，需求刚性极强。

1.2 行业侧的现实痛点#

低速自动驾驶运营企业普遍面临：

  • 多源协议碎片化：车端由不同 Tier1 供货，报文格式各自为政，自研接入成本高；
  • 自建平台重：小体量运营企业养不起一个完整的车联网平台团队；
  • 取证被动：事故发生后数据在车端、云端、监管平台三处割裂，整理一次取证材料动辄数天。

3. 竞争格局 [待验证]#

竞品类型 代表形态 优势 劣势（本产品的机会）
车企自建 TSP 乘用车厂的车联网平台 与车端深度耦合 面向 C 端体验，不满足 DSSAD 监管口径
通用车联网 PaaS 大厂物联网平台 生态全、扩展强 需要客户自己开发合规层，「买平台 ≠ 合规」
监管对接中间件小厂 单点对接工具 便宜、快 只做通道不做运营，取证与远驾能力缺失
运营企业自研 各家自建 贴合自身业务 成本高、协议跟进慢、人员流动即断档

本产品定位：面向低速自动驾驶运营企业的「合规网关 + 运营平台」一体机—— 按《平台数据对接接口文档》实现标准化云云对接（准入即用）， 同时交付事故取证、远驾接管、地图阻断等强监管业务闭环，而非裸通道。

3.1 差异化要点#

  1. 协议对齐即卖点：与上游 PDF 接口文档逐条对齐并留有偏差记录（接口文档附录）， 接入验收不会卡在协议理解分歧上；
  2. 取证链路完整：事故 → 下发取证请求 → 四方向视频归档 → 待归档催办（超时提醒）， 证据链每一环都有审计状态；
  3. 零依赖可落地：本地 profile（H2 文件库 + MQTT 关闭 + 报文模拟器）让售前 POC 可以「克隆即跑」，不依赖客户先备好 MySQL/Redis/Broker；
  4. 运维友好：探针退出码分级、备份三重校验 + 真恢复演练、应急剧本， 面向「没有专职运维的小团队」设计。
