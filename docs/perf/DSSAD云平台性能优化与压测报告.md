- **不作为生产性能承诺**。本机为单机 Windows 开发环境、H2 数据库、1 台车数据量，与「8 核服务器 + MySQL + 1000 台车」之间不存在可线性外推的关系。本文的价值在于**暴露量级与相对关系**（缓存收益、长尾形状、防护缺口），而不是给出生产 QPS。

### 0.4 指标口径（读数字前必看）

**口径 1：脚本输出的 QPS 是「单接口吞吐」，不是「系统总吞吐」。**

`load_test.py` 每个接口独立统计 `QPS = 该接口样本数 / 本轮墙钟`。6 个接口同时施加负载时，**系统总吞吐 ≈ 输出值 × 6**。例如第 6 轮的 `QPS 196.1` 对应约 **1180 req/s**。若不做此换算，会严重低估平台能力。

**口径 2：`--concurrency 13` 的实际并发是 6，不是 13。**

本轮采集所用脚本的任务模型是「每个接口 1 个 worker，串行发 N 次请求」。当接口数为 6 时，线程池中只有 6 个任务在跑，`max_workers=13` 的余量用不上。因此**实际在途请求数 = min(接口数, 并发数) = 6**。这一点在文档中如实标注（工具缺陷 F-T05），下一版脚本将按并发数拆分 worker。

**口径 3：业务成败以业务码为准，不以 HTTP 状态码为准。**

平台在 HTTP 200 的响应体内用业务码表达失败（如 `2001` 未授权、`3001` 车辆不存在）。鉴权失败路径**比正常查询更快**，只看 HTTP 状态码会把「全部被拒」误判成「性能极佳」。脚本已按 `code ∈ {0000}` 判定成功。

**口径 4：看分位数，不看均值。**

均值会被大量极快请求拉平，掩盖长尾。本报告同时给出 P50 / P95 / P99。其中 P50 反映"绝大多数请求走的路径"（缓存命中与未命中会明显分层），P95/P99 主要由 JVM GC 与操作系统调度抖动决定。

### 0.5 术语

| 术语 | 含义 |
|---|---|
| L1 / L2 | 一级缓存（进程内 Caffeine）/ 二级缓存（Redis，跨实例共享）|
| 墙钟（wall） | 一整轮压测从开始到结束的真实耗时 |
| 回源 | 缓存未命中，请求穿透到数据库查询 |
| 穿透 | 同「回源」 | 
| 冷启动轮 | 第 1 轮：JIT 未预热、连接池未建立、缓存为空 |
| 预热后轮 | 第 2 轮及之后 |

## 1 性能设计总览

### 1.1 先说清楚：在优化什么形状的负载

性能优化必须先明确压力形状，否则容易把力气花在不存在的问题上。本平台的负载有**两个截然不同的方向**：

| 方向 | 压力形状 | 量级 | 设计约束 |
|---|---|---|---|
| **读（查询侧）** | N 个前端 × 每 10 秒 × 4 个统计接口 | 并发低（数十）、**重复度极高**（同一份统计被反复读）| 要求**低延迟 + 高重复读的成本摊薄** |
| **写（接入侧）** | 车端 1Hz 位置报 + 60s 状态报 | 1000 台车 ≈ **1000 条/秒**、**8640 万行/天** | 要求**吞吐 + 不阻塞 MQTT 回调线程** |
| **读（取证侧）** | 单次查询跨度可达 1 小时 | 单车单小时 3600 点，大量历史数据 | 要求**降采样 + 传输体积控制** |

> **关键判断：本平台的性能矛盾不在"读的 QPS 有多高"，而在"写的行数有多大"。**
> 读侧哪怕 100 个前端同时刷新，也只是每秒几百次重复查询——加一层缓存即可消解；
> 写侧每天 8640 万行是**物理量**，只能用「批量写 + 保留期」这条路径解决，没有缓存可加。

这个判断直接决定了下面两项工作量的分配：**读侧靠 4 类手段（缓存/降采样/压缩/分页），写侧靠 3 类手段（缓冲批写/索引/保留期）**。

### 1.2 八项优化手段与代码落点

| # | 手段 | 代码落点 | 解决的压力 |
|---|---|---|---|
| 1 | **二级缓存**（L1 Caffeine + L2 Redis）+ 按缓存名独立 TTL | `common/cache/TwoLevelCache`、`TwoLevelCacheManager`、`config/CacheConfig`、`CacheProperties` | 读侧高重复查询 |
| 2 | **缓冲 + 定时批量落库**（1s 刷盘、5000/批）| `service/TelemetryService` | 写侧 1000 条/秒 |
| 3 | **JDBC 批量参数**（`batch_size`、`rewriteBatchedStatements`）| `application.yml` / `application-prod.yml` | 写侧单条 INSERT 往返 |
| 4 | **两段式轨迹降采样**（SQL 时间桶粗筛 + Douglas-Peucker 抽稀）| `service/TrackQueryService`、`common/util/TrackSimplifier` | 取证侧大跨度查询 |
| 5 | **入站队列 + 独立消费线程**（虚拟线程）| `mqtt/core/InboundMessageQueue`、`MqttInboundWorker` | 保护 MQTT 心跳、故障隔离 |
| 6 | **遥测保留期清理**（每天 03:30 分批 DELETE）| `service/TelemetryRetentionService` | 写侧无限增长 |
| 7 | **报文留痕采样**（full / sampled / event-only）| `dssad.audit.mode`、`MqttAuditService` | 审计表体积 |
| 8 | **HTTP 压缩 + 分页上限 + 线程池/连接池配置** | `application*.yml` | 传输体积、并发上限 |

### 1.3 手段与压力的对应关系（一图定性）

| 压力源 | 主要手段 | 次要手段 | 本次是否实测 |
|---|---|---|---|
| 大屏 10 秒刷新风暴 | ①二级缓存 | ⑧HTTP 压缩 | ✅ 第 4 章 |
| 千车 1Hz 写入 | ②缓冲批写 | ③JDBC 批量、⑥保留期 | ❌ 第 6 章推演 |
| 大跨度轨迹查询 | ④两段式降采样 | ⑧分页上限 | ❌ 第 7.2 节代码核查 |
| MQTT 回调阻塞 | ⑤队列 + 独立消费线程 | — | ❌ 无 Broker |
| 车端异常高频上报 | 限流（**实测未生效**）| ⑤队列容量兜底 | ✅ 第 5 章（反面结论）|
| 磁盘无限增长 | ⑥保留期 | ⑦采样 | ❌ 由《数据库设计说明书》覆盖 |

## 2 压测方案

### 2.1 三个实验

| 编号 | 实验 | 目的 | 负载 |
|---|---|---|---|
| **DS-1** | 只读接口基线 | 摸清现状：多快、多稳、长尾多长 | 6 接口 × 120 请求 × 6 轮，并发 13（实际 6）|
| **DS-2** | 缓存 A/B 对照 | 量化缓存收益（唯一能证明缓存"有用"的方式）| 同负载，A 关缓存 / B 开缓存，各 4 轮 × 200 请求 |
| **DS-3** | 限流行为验证 | 验证防护能力是否真的生效 | 同一 VIN 连续 130 次请求（阈值 100 次/分钟）|

**为什么缓存收益必须做 A/B 对照？**
只跑一遍「开了缓存很快」得不出结论——快可能是因为 JIT 预热、连接池预热、H2 内存库本身快。**只有把「缓存」这一个变量单独打开/关闭，其余完全相同，差值才有归因意义。** DS-2 的两组实例由同一个 jar、同一份配置启动，唯一的差别是启动参数：

```bash
# A 组：关闭本平台缓存管理器 + 关闭 Spring 缓存（NoOp）
--dssad.cache.enabled=false --spring.cache.type=none
# B 组：本地默认（二级缓存管理器生效 → L1 Caffeine）
（不加参数）
```

### 2.2 负载参数及理由

| 参数 | 取值 | 理由 |
|---|---|---|
| 并发 | 13（实际 6）| 约等于「十来个运营人员同时开着大屏与列表页」；受工具模型限制实际为 6（口径 2）|
| 每接口请求数 | 120（DS-1）/ 200（DS-2）| 足以让 P99 落在真实样本上；200 时 P99 由第 2 个最慢的请求决定，波动可控 |
| 轮数 | 6 / 4 | 第 1 轮冷启动，后续观察收敛；6 轮可见吞吐爬升全过程 |
| 超时 | 10s | 远大于观测值（<100ms），避免超时干扰统计 |
| 接口选择 | 6 个查询热点 | 与前端大屏、列表页一一对应；**全部为 GET，对预发环境安全** |

### 2.3 观测与判定口径

- **成功判定**：`HTTP 2xx` **且** 业务码为 `0000`。
- **延迟统计**：仅统计成功样本（失败样本的耗时不代表业务能力）。
- **分位数算法**：最近秩法（`int(round(p/100 × n + 0.5)) - 1`），比线性插值保守，小样本下不会被单点平滑掉。
- **缓存指标**：读 `/api/v1/monitor/cache`（平台把 L1/L2 命中数、穿透数、命中率暴露成接口，因为**缓存失效是静默的**：命中率掉到 0 时接口仍返回正确结果，只表现为数据库压力上升）。

### 2.4 复现命令

```bash
# 起服务（本地 profile，默认端口 8080）
java -jar target/dssad-cloud-platform.jar --spring.profiles.active=local

# 基线压测（脚本自动登录换令牌）
python perf/load_test.py --base-url http://127.0.0.1:8080 \
    --concurrency 13 --rounds 6 --requests-per-endpoint 120 \
    --username admin --password '<口令>'

# 限流探针（同一 VIN 连打 130 次）
python perf/rate_limit_probe.py --base-url http://127.0.0.1:8080 \
    --vin <真实VIN> --count 130 --username admin --password '<口令>'
```

## 3 实测结果一：只读接口基线（DS-1）

**环境**：H2 文件库（1 台车 + 1 起事故）、缓存启用（L1）、6 接口 × 120 请求 × 6 轮。

### 3.1 全量数据

**第 1 轮（冷启动）— 墙钟 1.09s**

| 接口 | 样本 | 失败 | 单接口 QPS | 均值 | P50 | P95 | P99 |
|---|---|---|---|---|---|---|---|
| 总览大屏 | 120 | 0 | 110.3 | 3.9ms | 2.7ms | 5.7ms | 19.7ms |
| 事故趋势 | 120 | 0 | 110.3 | 3.4ms | 2.7ms | 4.3ms | 7.0ms |
| 故障分类分布 | 120 | 0 | 110.3 | 3.4ms | 2.7ms | 5.0ms | 12.8ms |
| 车辆列表 | 120 | 0 | 110.3 | 9.0ms | 5.5ms | 16.7ms | 23.9ms |
| 链路监控 | 120 | 0 | 110.3 | 3.4ms | 2.7ms | 5.7ms | 17.1ms |
| 缓存与限流 | 120 | 0 | 110.3 | 3.2ms | 2.7ms | 5.2ms | 17.1ms |

**第 6 轮（收敛）— 墙钟 0.61s**

| 接口 | 样本 | 失败 | 单接口 QPS | 均值 | P50 | P95 | P99 |
|---|---|---|---|---|---|---|---|
| 总览大屏 | 120 | 0 | 196.1 | 1.7ms | **1.4ms** | 2.1ms | 17.2ms |

| 车辆列表 | 120 | 0 | 196.1 | 5.1ms | **2.0ms** | 16.3ms | 16.9ms |
| 链路监控 | 120 | 0 | 196.1 | 1.7ms | **1.3ms** | 2.3ms | 17.2ms |
| 缓存与限流 | 120 | 0 | 196.1 | 1.9ms | **1.4ms** | 2.7ms | 17.4ms |

**中间轮次的墙钟与吞吐**

| 轮次 | 墙钟 | 单接口 QPS | 系统总吞吐（×6，推算）|
|---|---|---|---|
| 1 | 1.09s | 110.3 | ≈ 660 req/s |
| 2 | 1.01s | 118.7 | ≈ 712 req/s |
| 3 | 1.12s | 107.0 | ≈ 642 req/s |
| 4 | 0.95s | 125.9 | ≈ 755 req/s |
| 5 | 0.62s | 193.8 | ≈ 1163 req/s |
| 6 | 0.61s | 196.1 | ≈ 1180 req/s |

### 3.2 吞吐为什么随轮次上升：三个预热过程

第 1 轮 → 第 6 轮，P50 从 2.7ms 降到 1.4ms（**-48%**），吞吐提升 **+78%**。这不是"越跑越快"的玄学，而是三个可以明确归因的预热：

1. **JIT 预热**（贡献最大）。前几百次调用以解释执行运行，热点方法被 C2 编译后才是真实性能。第 3 轮出现轻微回落（107.0）正是编译线程与业务线程争抢 CPU 的表现，第 5 轮完成后趋于稳定。
2. **连接池与数据库预热**。HikariCP 从 `minimum-idle` 扩张到实际需要的大小，H2 的页缓存被填充。
3. **缓存预热**。第 1 轮每个缓存名发生 1 次穿透（回源），之后全部命中（见 4.4）。

> **工程含义**：生产环境的容器如果没有预热（或流量入口一上来就全量），**首批用户会遇到比稳态高约 1 倍的延迟**。建议发布后先由探针打一轮热点接口再放开流量，或启用 K8s `startupProbe` + 预热脚本。

### 3.3 分位数解读：为什么 P50 和 P99 差一个数量级

| 现象 | 观测 | 解释 |
|---|---|---|
| P50 稳定在 1.3~1.4ms | 全部 6 接口 | 缓存命中路径：`Caffeine.getIfPresent` + 序列化，纯内存操作 |
| P99 稳定在 14~28ms | 全部 6 接口，且与轮次无明显相关 | **不在业务代码里**：JVM young GC 停顿、Windows 线程调度、同机压测客户端抢占 CPU。每轮 720 个样本，P99 只由约 7 个样本决定，极易被单次 GC 拉高 |
| 车辆列表 P50 显著高于其他接口 | 2.0ms vs 1.4ms；P95 达 16.3ms | 它是**唯一不走缓存**的接口：`JpaSpecificationExecutor` 动态条件 + 分页 + 一次 `count` 查询，至少 2 次数据库往返 |
| 每轮 P95 波动可达 ±40% | 如总览大屏 P95：5.7 → 6.7 → 6.3 → 20.7 → 3.9 → 2.1ms | 同上，长尾由环境噪声主导。**因此本报告的任何结论都不建立在单独一轮的 P95 之上**——第 4 轮的 P95 飙高（20.7ms）与第 5 轮的回落（3.9ms）不是性能变化，而是噪声 |

> **可复现的观测模式**：第 4 轮所有接口的 P95 同时跳到 20~24ms，说明这是一次全系统级的停顿（GC 或系统调度），而不是某个接口的问题。**跨接口同时跳变 = 环境噪声；单接口孤立跳变 = 该接口的问题。** 这是判断"性能回归 vs 环境抖动"最快的方法。

### 3.4 结论（DS-1）

- 6 个查询热点接口在稳态下 **P50 1.3~2.0ms、P95 2.1~16.3ms**，无失败样本，无错误码。
- 系统总吞吐 ≈ **1180 req/s**（稳态），远超大屏刷新的实际需要（100 个前端 × 每 10 秒 × 4 接口 = **40 req/s**），**读侧余量约 30 倍**。
- 唯一较慢的接口是「车辆列表」（不走缓存），但其 P50 2.0ms 仍在可接受范围。
- 长尾（P99）由 JVM/OS 环境噪声主导，不是平台代码的瓶颈。

## 4 实测结果二：二级缓存收益（DS-2 对照实验）

### 4.1 实验设计

| 项 | A 组（对照）| B 组（实验）|
|---|---|---|
| 启动参数 | `--dssad.cache.enabled=false --spring.cache.type=none` | 无（本地默认）|
| 缓存管理器 | `NoOpCacheManager`（每次请求都回源）| `TwoLevelCacheManager`（L1 Caffeine）|
| 监控端点报告 | `模式 = NoOpCacheManager` | `模式 = L1(Caffeine)` |
| 数据库 | H2 **内存库** `perfA` | H2 **内存库** `perfB` |
| 数据量 | 1 台车 + 1 起事故（注入同量场景）| 1 台车 + 1 起事故（同 VIN、同场景）|
| 负载 | 6 接口 × 200 请求 × 4 轮 | 完全相同 |

**为什么用内存库而不是同一个文件库？** 第一次尝试让两个实例共享 H2 文件库（`AUTO_SERVER=TRUE`），结果先启动的实例占住文件后**第二个实例的 DataSource 初始化失败**（`Unable to determine Dialect without JDBC metadata`），对照实验直接作废。改用各自独立的内存库后两个实例均正常启动——这也侧面说明：**同一个 H2 文件库不要被多个 JVM 同时打开，即使 `AUTO_SERVER=TRUE` 也不可靠。**

### 4.2 冷启动轮对比：缓存价值最清晰的一组

第 1 轮两组都毫无预热（JIT 冷、连接池冷、缓存空），是归因最干净的一组：

| 指标 | A 组（无缓存）| B 组（有缓存）| 变化 |
|---|---|---|---|
| **整轮墙钟** | 4.00s | **2.07s** | **-48%** |
| 单接口 QPS | 50.0 | **96.8** | **+94%** |
| 总览大屏 P50 | 20.1ms | **3.1ms** | **-85%（6.5 倍）** |
| 事故趋势 P50 | 15.9ms | **3.1ms** | **-81%（5.1 倍）** |
| 故障分类分布 P50 | 3.9ms | **3.1ms** | -21% |
| 车辆列表 P50 | 5.0ms | 6.7ms | +34%（**该接口不走缓存**，差异来自 B 组负载更密）|
| 链路监控 P50 | 2.8ms | 3.2ms | +14%（该接口直读内存计数器，本来就不查库）|
| 缓存与限流 P50 | 2.8ms | 3.1ms | +11%（同上）|

**逐条解读**：

- **总览大屏与事故趋势是缓存的最大受益者**。这两个接口一个要横跨 12 个仓储做十几次 COUNT，另一个是「逐日窗口计数」（days=7 时 14 次 COUNT），在无缓存时首轮直接 20.1ms / 15.9ms；缓存命中后降到 3.1ms。这正是设计意图（`DashboardService` 类注释里写明"全平台查询密度最高的入口"）。
- **车辆列表与链路监控不受影响，这是预期的**。前者不走 `@Cacheable`，后者直接读 `InboundMessageQueue.size()` 等内存计数器。它们的 P50 在 B 组略高，是因为 B 组整轮墙钟更短、瞬时压力更集中——**这是一个有用的反证：如果这两个接口也在 B 组大幅变快，说明测量的不是缓存效应，而是别的干扰因素。**
- **故障分类分布收益最小（-21%）**。它只查 `t_fault_item` 一张小表，数据量极小，缓存省下的时间有限。**缓存收益与"回源成本"成正比，与"数据量"成正比**——这条在 4.5 节会反向用于说明为什么实测值偏低。

### 4.3 预热后轮对比：收益为什么被摊薄

第 4 轮（A 组也已充分预热）：

| 指标 | A 组（无缓存）| B 组（有缓存）| 变化 |
|---|---|---|---|
| 整轮墙钟 | 1.82s | 1.67s | -8% |
| 单接口 QPS | 110.0 | 119.6 | +9% |
| 总览大屏 P50 | 3.9ms | **1.7ms** | -56% |
| 事故趋势 P50 | 2.2ms | 2.3ms | ≈0 |
| 故障分类分布 P50 | 1.8ms | 1.6ms | -11% |
| 车辆列表 P50 | 2.0ms | 2.6ms | +30% |

A 组第 4 轮的总览大屏 P50 从首轮 20.1ms 掉到 3.9ms——**这不是缓存带来的，是 JIT 与 H2 内存库预热带来的**。当数据库查询本身只要 1~2ms 时，缓存能省下的绝对时间自然变小。

> **这就是为什么"缓存收益"这个数字必须标注前提**：在 H2 内存库 + 1 行数据的极端条件下，回源成本几乎为零，缓存收益被压缩到下界。**第 4 轮的数据不代表缓存在生产无用，只代表"本机小数据量下无用"。**

### 4.4 缓存命中率实测

DS-1 压测结束时读 `/api/v1/monitor/cache`：

| 缓存名 | 形态 | L1 命中 | L2 命中 | 穿透 | 命中率 |
|---|---|---|---|---|---|
| `dashboardOverview` | 仅 L1 | 719 | 0 | 1 | **99.86%** |
| `dashboardTrend` | 仅 L1 | 719 | 0 | 1 | **99.86%** |
| `dashboardFaultCategory` | 仅 L1 | 719 | 0 | 1 | **99.86%** |
| `dashboardFaultVehicles` | 仅 L1 | 0 | 0 | 0 | 0%（本轮未调用）|
| **合计** | | **2157** | 0 | **3** | **99.86%** |

**99.86% = 719 命中 / 1 穿透**，怎么读：

- 720 次请求 = 6 轮 × 120 次。**6 轮里只有 3 次穿透**，意味着每个缓存名在 6 轮中只回源了 1 次 —— 即**第 1 轮的第 1 次请求**。
- 原因：本地 profile 的 `dssad.cache.l1-default-ttl-seconds: 10`，而每轮墙钟仅 0.6~1.1 秒。**6 轮总计不到 7 秒，全部落在同一个 TTL 窗口内**，因此缓存一次都没过期。
- `dashboardFaultVehicles` 命中为 0 是正常的：压测的 6 个接口里没有调用它的那个（`/api/v1/dashboard/fault-vehicles`），它被声明并预创建，但没被访问。

> **口径提醒**：这个 99.86% 是**「TTL 窗口内的高频重复读」**场景下的命中率，不代表生产。生产大屏每 10 秒刷新、TTL 配置 5~60 秒（见 `DashboardService` 注释），命中率的量级会落在**70%~95%**区间。把 99.86% 当作生产预期会高估收益。

### 4.5 为什么实测的缓存收益是**下界**

三条低估因素，逐条对应：

1. **数据库太快**。H2 内存库 + 1 行数据，一次 COUNT 的成本远低于生产 MySQL（千万行表的二级索引扫描 + 磁盘 IO）。缓存的价值等于"省下的回源成本"，回源越贵，缓存越值钱。
2. **数据量太小**。`t_vehicle_track_point` 在生产是 8640 万行/天（见《数据库设计说明书》5.2）。大屏的轨迹类统计在数据量大时会从"索引扫描"退化为"索引扫描 + 回表"，缓存收益按数量级放大。
3. **无并发放大**。本实验实际并发只有 6，缓存"挡住重复读"的价值在并发高时才会显现——N 个前端同时刷新时，无缓存意味着 N 次并发的重复 COUNT 挤占同一个连接池（生产 `maximum-pool-size: 20`）。

**结论**：**-85% / -81% 应当被理解为"缓存收益的下限"**。生产环境（MySQL + 真实数据量 + 多前端并发）的收益只会更大，且更重要的收益不是延迟，而是**把数据库从"被大屏刷新打满"中解放出来**。

### 4.6 结论（DS-2）

- 二级缓存**确实生效**（命中率 99.86%、`模式 = L1(Caffeine)` 可查、A/B 差异显著），不是"配了但没生效"的静默失败。
- 冷启动场景下：整轮吞吐 **+94%**、关键接口 P50 **-81% ~ -85%**。
- 收益集中在**回源成本高的统计类接口**；对不走缓存的接口（车辆列表）无影响——这是符合预期的正确行为。
- **L2（Redis）在本轮完全未验证**（本地 `dssad.redis.enabled=false`，监控端点报告 `仅L1`、`L2 命中 0`）。生产是多实例部署、L2 承担跨实例一致性，**上线前必须在启用 Redis 的环境重跑一次 DS-2**，重点观察 `l2Hits` 是否随实例数增长而上升。

## 5 实测结果三：限流与保护能力（DS-3）

这是本轮压测**最重要的发现**，且是一个**反面结论**。

### 5.1 设计意图：限流器怎么写的

`ratelimit/RateLimiter` 实现的是**滑动窗口计数**（sliding window counter），对应上游文档 9.1 的两条指标：

| 指标 | 配置项 | 值 |
|---|---|---|
| 单车辆 HTTP 接口 | `dssad.rate-limit.http-per-minute` | 100 次/分钟 |
| 单车辆 MQTT 发布 | `dssad.rate-limit.mqtt-per-second` | 10 条/秒 |

算法要点（代码里已实现且**有单测**）：

- 双窗口加权：`estimated = previousCount × (1 − elapsedRatio) + currentCount`，把上一窗口的计数按本窗口已流逝比例线性衰减，抑制固定窗口在边界处的 2 倍突刺。
- 只占 2 个 Redis/Caffeine 键，判定常数级往返。
- 被拒绝的请求**不计入计数**，避免"持续探测导致永久封死"。
- 存储异常时**放行**（保护性旁路优先于准确性）。

监控端点也把状态暴露得很完整：

```json
"rateLimit": { "enabled": true, "httpPerMinute": 100, "mqttPerSecond": 10,
               "algorithm": "sliding-window-counter" }
```

**读到这一步，一切看起来都是对的。**

### 5.2 动态验证：同一 VIN 连打 130 次

用真实存在的车辆（先经 `/api/v1/simulator/scenario/accident` 注入场景创建 `LSVAAPERF00000001`，并确认 `/api/v1/vehicles/{vin}` 返回 `0000`），对**同一个 VIN** 连续请求 130 次，跨越配置阈值 100：

```
============================================================
限流探针  target=http://127.0.0.1:18080/api/v1/vehicles/LSVAAPERF00000001  次数=130  鉴权=已登录
============================================================

成功 130 次，被拒（4001）0 次，鉴权失败 0 次，其他失败 0 次

[判定]
  ⚠️ 未观察到任何限流：同一 VIN 连续 130 次请求，无一次返回 4001。
     全部 130 次均为业务码 0000，即 130 次请求都完整走完了业务处理。
     限流判定本应**先于**业务处理执行，故结论明确：
     请求链路上不存在调用 RateLimiter.tryAcquireHttp() 的 Filter/Interceptor，
     `dssad.rate-limit.*` 目前只是一份「可被监控端点读出来的配置」。
```

**130 次请求，100% 成功，0 次被拒。** 而配置写的是 100 次/分钟。

**佐证：这不是"限流阈值太高所以没触发"。** 130 次请求 / 约 2 秒内完成，若限流生效，第 101 次必须返回 `4001`。且限流判定本应在业务处理**之前**（否则攻击者只要构造"处理很慢"的请求就能绕过），因此"车辆存在、业务成功"不构成绕过理由。

### 5.5 修复方案（已于 v1.1 落地）

> **实际实现与本节当初的草案有两处关键差异**，如实记录（草案保留在后供对照）：
>
> 1. **接线面不同：企业侧 `/enterprise/api/v1/**`，而非管理端 `/api/v1/**`**。
>    上游文档 9.1 的「·车」配额约束的是**对接接口**（企业按车辆发起的调用）；
>    管理端 `/api/v1/**` 是本平台自建的操作员界面，不在上游文档约定范围内，
>    其客户端是操作员而非车辆，按 VIN 限流语义不成立。
>    限流键 VIN 在企业侧 4 个接口的请求体里（`@NotBlank String vin`），
>    由已存在的 `CachedBodyRequestWrapper`（签名过滤器为防重放已实现 body 缓存）提取。
> 2. **形态不同：Filter 而非 Interceptor**——需要在进入业务层之前读 body 判定，
>    且签名过滤器本身就是 Filter，同一层内保持形态一致。
>    实际实现：`ratelimit/EnterpriseRateLimitFilter`（order = 签名过滤器 +1），
>    拒绝响应按接口文档 2.7.1 契约返回 HTTP 200 + body `4001`（非 429，
>    对端按 `body.code` 解析），附 `Retry-After: 60`。
>    **接线时堵住了一个「静默失效」隐患**：过滤器若因装配顺序变化拿不到已包装的
>    请求，会自行包装而不是跳过判定——否则限流会随过滤器顺序调整无声消失。

<summary>原草案（已被上述实现取代，保留供对照）</summary>

最小改动、最小侵入的方案是在 `WebConfig` 已注册的拦截器链上加一个限流拦截器：

```java
// security/RateLimitInterceptor.java（新增）
@Component
@RequiredArgsConstructor
public class RateLimitInterceptor implements HandlerInterceptor {

    /** 限流主体提取：优先取路径变量的 vin，其次取 X-Vin 头。 */
    private static final Pattern VIN_IN_PATH = Pattern.compile("/api/v1/vehicles/([A-Za-z0-9]{6,20})");

    private final RateLimiter rateLimiter;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String vin = extractVin(request);
        if (vin == null) {
            return true;   // 非车辆维度的接口不参与车端限流
        }
        if (!rateLimiter.tryAcquireHttp(vin)) {
            throw new BizException(ErrorCode.RATE_LIMITED);
        }
        return true;
    }

    private String extractVin(HttpServletRequest request) {
        Matcher m = VIN_IN_PATH.matcher(request.getRequestURI());
        if (m.find()) {
            return m.group(1);
        }
        return request.getHeader("X-Vin");
    }
}
```

并在 `WebConfig` 注册（保持与令牌拦截器同一批路径，排除登录/健康检查）：

```java
registry.addInterceptor(rateLimitInterceptor)
        .addPathPatterns("/api/v1/**")
        .excludePathPatterns("/api/v1/auth/login", "/api/v1/monitor/health-check",
                             "/api/v1/simulator/**", "/error");
```

</details>

### 6.1 缓冲-批量刷盘模型

`TelemetryService` 的核心设计是「**内存缓冲 + 定时批量落库**」：

```
Paho 回调线程 ──入队（微秒级）──> ConcurrentLinkedQueue ──每秒 drain──> saveAll(≤5000/批) ──> MySQL
                                        │
                            （缓冲上限 100,000，超限丢弃并计数）
```

| 参数 | 值 | 代码位置 | 取舍 |
|---|---|---|---|
| 缓冲上限 | 100,000 | `TelemetryService.MAX_BUFFER_SIZE` | 约 100 秒的 1000 车 1Hz 流量；宁可丢采样点也不能 OOM |
| 单批上限 | 5,000 | `FLUSH_BATCH_SIZE` | 避免单次事务过大、undo log 膨胀 |
| 刷盘周期 | 1s | `@Scheduled(fixedDelay = 1_000)` | 「入库延迟」与「批大小」的折中 |
| JDBC 批大小 | 200（本地）/ 500（生产）| `application*.yml` | 配合 `rewriteBatchedStatements=true` 合并为多值 INSERT |
| 优雅停机 | `@PreDestroy` 刷盘 | `flushOnShutdown()` | 停机不丢最后一批 |

### 6.2 量化推算：1000 台车 1Hz

| 项 | 推算 | 说明 |
|---|---|---|
| 入站报文速率 | **1000 条/秒** | 1000 台 × 1 次/秒（另有 60s 一次的状态报，量级为 1/60，可忽略）|
| 每秒刷盘次数 | **1 次** | 定时任务 |
| 每次批大小 | **1000 行**（轨迹表）| 落在 `FLUSH_BATCH_SIZE` 5000 之内，单事务 |
| 合并后 SQL 语句数 | 约 **2~5 条** INSERT | 1000 行 ÷ JDBC batch_size 500（生产）= 2 批；`rewriteBatchedStatements` 将其合并 |
| 每秒数据库往返次数 | **约 2~5 次** | 对比「每条报文一次 INSERT」的 1000 次往返，**降低约 200~500 倍** |
| 日增行数 | 8640 万行（轨迹）+ 144 万行（状态）| 与《数据库设计说明书》5.2 一致 |
| 日增体积 | 约 **14.3 GB**（轨迹，178 B/行）+ 0.33 GB（状态）| 同上 |

**关键结论：批量写入把「每秒 1000 次事务提交」压成「每秒 1 次事务、2~5 次往返」，这是千车规模能跑起来的前提。** 单条 INSERT 方案在 MySQL 上每秒 1000 次提交会直接撞在 fsync 与网络往返上，且没有优化空间。

### 6.3 参数取舍的三个边界

1. **刷盘周期 1s 的风险**：进程崩溃（非优雅停机）最多丢 1 秒数据（≤1000 行）。对轨迹取证场景可接受（车端本地有存、可重发）。若要零丢失，需改为「消息级确认 + WAL」，代价是每条报文一次 fsync。
2. **缓冲上限 100,000 的风险**：数据库持续慢于 1000 行/秒时，缓冲约 100 秒后开始丢弃，日志每累积 10000 条报一次 ERROR。**这是"静默降级"的设计**——平台不会因为写不进去而挂掉，但会丢数据。监控端点 `/api/v1/monitor/mqtt` 暴露了 `telemetryBuffered` 与 `telemetryDropped`，**必须对这两个指标配告警**（`telemetryBuffered` 持续 > 10000 或 `telemetryDropped` 增长即告警）。
3. **索引代价**：`t_vehicle_track_point` 上的二级索引（92 B/行，见数据库文档 5.1）会使写入成本增加约一倍。这是**为了查询必然付出的代价**（无索引的轨迹查询等于全表扫描），但意味着写入侧的性能预算要按"索引放大后"估算。

### 6.4 入站队列与丢弃策略

| 组件 | 容量 | 满时行为 | 理由 |
|---|---|---|---|
| `InboundMessageQueue` | 20,000（约 10 倍峰值冗余）| **丢弃最旧的一条**并计数 | 积压说明消费能力不足，保留最新数据比保留全部历史更有价值（历史可从车端重发补齐）|
| `OfflineMessageQueue` | 10,000（`offline-cache-size`）| 按优先级淘汰**最低优先级**消息（`droppedLowPriority` / `droppedByPressure` 分开计数）| 远驾接管、任务指令不能因容量满被丢，而遥测可以 |

**这两个队列有本质区别**：入站队列丢的是「已经收到的报文」（上游还有机会重发），离线队列丢的是「还没发出去的下行指令」（丢了就真丢了）。因此离线队列必须做优先级淘汰，入站队列只需要保住最新的。

### 6.5 本章明确未验证的部分

| 未验证项 | 风险 | 验证方式 |
|---|---|---|
| 1000 条/秒连续写入时的实际批处理耗时 | 若单次 `saveAll(1000)` 超过 1 秒，队列会持续积压直至丢弃 | 用 `SimulatorController` 注入高频报文，观察 `telemetryBuffered` 是否稳定在低位 |
| MySQL 真实 `rewriteBatchedStatements` 生效情况 | 未生效则退化为逐条 INSERT，性能差 5~10 倍 | 开 `general_log` 或 ProxySQL 抓包，确认生成的是多值 INSERT |
| 索引维护对写入的影响 | 轨迹表有二级索引，写入放大约 1 倍 | `SHOW TABLE STATUS` 观察 `data_length` 与 `index_length` 比例 |
| 保留期清理对写入的影响 | 每天 03:30 分批 DELETE 会与业务写入争抢 IO 与锁 | 在预发环境手动触发 `scheduledPurge`，观察主从延迟与写入 P99 |

### 7.1 虚拟线程：为什么没做 A/B 对比

配置状态：

| 位置 | 配置 | 值 |
|---|---|---|
| Tomcat 请求处理 | `spring.threads.virtual.enabled` | prod: `true`；local: 未设置（默认平台线程）|
| MQTT 消费线程 | `dssad.mqtt.virtual-threads` | `true`（代码默认）|
| 消费线程数 | `dssad.mqtt.consumer-threads` | 4 |

**未做 A/B 的原因**：本机压测的并发只有 6，且请求几乎全是"缓存命中 + 内存返回"，平台线程池（`max-threads: 200`）根本用不满——**此时切换虚拟线程不会有可测量的差异**。虚拟线程的价值要在大并发 + 阻塞型 IO 下才显现，而本机不具备复现条件。

**纳入核查的两条判断**：

1. **虚拟线程的收益点是对的**。`MqttInboundWorker` 的消费循环是纯阻塞型（`queue.take()` + JDBC 往返），正是虚拟线程的设计目标场景。代码注释里"把 `consumer-threads` 变成可以放心调大的旋钮"这个定位准确。
2. **要注意一个语义变化**：启用虚拟线程后，Tomcat 的 `max-threads: 200` **不再是并发上限**，请求会无限制地被受理，真正的排队点转移到 HikariCP（生产 `maximum-pool-size: 20`）。这意味着**数据库连接池成为了唯一的并发控制点**，若连接池配置不当（如 `connection-timeout: 3000` 到期抛异常），表现会是"突发流量下大批请求 3 秒后失败"而不是"排队等待"。**上线前需在预发环境验证：并发 200 时是否出现连接获取超时。**

### 7.2 轨迹两段式降采样

`TrackQueryService` 的降采样分两段，这个设计值得单独说明：

| 阶段 | 手段 | 作用 |
|---|---|---|
| SQL 侧 | 先 `count` 判定量级；量大时按时间桶粗筛（`mod(ts, bucket) < 1000`）| 把几十万行压到万级，**在数据库侧就减少数据搬运** |
| 内存侧 | Douglas-Peucker 抽稀（容差 8m）| 在形变可控的前提下继续压到千级 |

**设计上正确的一点**：`alignBucket()` 把时间桶对齐到 1 秒整数倍。因为数据是 1Hz 上报，若桶不是 1000ms 的整数倍，会出现"某些桶命中 0 次或 2 次"，轨迹会出现空洞或抖动 —— 这是一个只有理解了数据上报周期才能想到的边界问题。

**两个已知限制**（属《详细设计说明书》已记录项）：

- `P-10`：抽稀容差是全局单一值（`dssad.api.track-simplify-tolerance: 8.0`），大屏概览与事故复盘需要不同精度，应改为接口可选参数。
- `TrackSimplifier` 最坏复杂度 O(n²)（单调点集）。代码注释称 8.6 万点单次约 20ms，本轮未复现验证；若遇到极端直线路段（如高速长直道）可能出现明显尖峰，建议补一条性能回归测试。

### 7.3 报文留痕采样：一行配置省 95%

| 模式 | 留痕比例 | 1000 台车日增体积 | 适用 |
|---|---|---|---|
| `full` | 100% | **59.6 GB/天** | 仅供参考，任何生产环境都不应使用 |
| `sampled` | 5% | 2.98 GB/天 | **生产默认**（`application-prod.yml`）|
| `event-only` | ≈0.1% | 0.06 GB/天 | 磁盘紧张时 |

> **工程建议**：磁盘不足时**优先降采样率，而不是缩短轨迹保留期**。理由是留痕有"事件类报文始终全量"兜底（`MqttAuditService` 对事故/故障类报文不做采样），而轨迹是事故回溯的原始证据，删了就没了。这条与《数据库设计说明书》5.3 的建议一致。

### 7.4 传输与并发配置核查

| 配置 | 值 | 评价 |
|---|---|---|
| `server.compression.enabled` | `true`（JSON/text，>2KB 才压缩）| 合理。门槛 2048 字节避免为小响应付出压缩开销；大屏总览这类响应用压缩收益明显 |
| `server.tomcat.threads.max` | 200 | 平台线程模式下合理；虚拟线程模式下失去意义（见 7.1）|
| `spring.datasource.hikari.maximum-pool-size` | 20（生产）| 按"8 核 × 2 + 有效磁盘数"估算。**虚拟线程启用后这是真正的并发上限**，需实测验证 |
| `dssad.api.max-page-size` | 200 | 服务层还有 `Math.min(Math.max(size,1), maxPageSize)` 二次钳制，防止前端传 `size=100000` 拖垮数据库 |

## 8 瓶颈分析与容量推算

### 8.1 当前瓶颈排序

**读路径：不构成瓶颈。** 稳态 P50 1.3~2.0ms，系统总吞吐约 1180 req/s，而实际业务需要约 40 req/s（100 个前端 × 10 秒 × 4 接口），**余量约 30 倍**。

**写路径：唯一的真实瓶颈。** 1000 台车每天 8640 万行轨迹、约 14.3 GB，这是物理量，无法用缓存或并发优化消除，只能靠：

| 手段 | 效果 | 当前状态 |
|---|---|---|
| 批量写入 | 往返次数降低 200~500 倍 | ✅ 已实现 |
| 保留期清理 | 把"无限增长"变成"稳态容量" | ✅ 已实现（`TelemetryRetentionService`）|
| 留痕采样 | 审计表体积 -95% | ✅ 已实现（`sampled`）|
| 迁往时序库 | 压缩率与聚合查询数量级改善 | ❌ 未做（数据库文档 8.6 已提出）|

**存储：与写路径同一个问题的另一面。** 除轨迹表外，媒体文件是最大单项（1080p H.265 每起事故约 20MB，见数据库文档 5.2）。

### 8.2 与数据库容量估算的互证

数据库文档第 5 章的容量测算与本报告的写入推演**必须能对上**，否则说明两者有一方算错：

| 项 | 《数据库设计说明书》5.2 | 本报告 6.2 | 是否一致 |
|---|---|---|---|
| 轨迹行数/天（1000 车）| 8640 万 | 8640 万（1000 × 86400）| ✅ |
| 轨迹体积/天 | 14.32 GB（178 B/行）| 14.3 GB | ✅ |
| 状态行数/天 | 144 万 | 144 万（1000 × 1440）| ✅ |
| 状态体积/天 | 0.327 GB | 0.33 GB | ✅ |
| 留痕 `sampled` 日增 | 2.98 GB/天 | 2.98 GB/天（59.6 × 5%）| ✅ |

**交叉核对结论：写入速率推算与行占用测算自洽。** 两个数字分别来自"报文频率"与"行格式测算"两条独立路径，结果一致，说明 `178 B/行` 与 `1Hz/车` 这两个基础假设可靠。

**由此得到一条可执行的运维规则**：`dssad.retention.track-point-days` 必须由磁盘容量反推，而不是拍脑袋定：

| 数据盘可用空间 | 建议 `track-point-days` | 说明 |
|---|---|---|
| 350 GB | **15 天** | 215 GB，满足"事发后回溯近两周"的常规取证需求 |
| 750 GB | 30 天 | 430 GB，但需同时保留状态流水 180 天（59 GB）|
| 2 TB | 90 天 | 1289 GB，或改迁时序库 |

### 8.3 三种"先崩"场景推演

按"最可能先发生"排序：

**场景 1：磁盘写满（最可能）**
- 触发条件：`track-point-days` 配错（如设为 0 或过大），或车辆数从试点的几十台快速扩到上千台而没改配置。
- 表现：轨迹表涨到数十亿行 → 查询变慢 → 清理任务（分批 DELETE）耗时超过 1 天 → **清理追不上增长**，最终 MySQL 无法写入。
- 为什么最可能：这是**唯一随时间必然恶化的方向**，其他问题都需要特定触发条件。
- 前置信号：`data_length + index_length` 日增超预期（应约 14 GB/天）、`TelemetryRetentionService` 的清理日志耗时持续上升。

**场景 2：一台异常车端打满消费能力（次可能）**
- 触发条件：某车端因程序缺陷以远高于 1Hz 的频率上报（如重连后循环补发）。
- 表现：`InboundMessageQueue` 积压持续增长 → 开始丢弃、`droppedCount` 上升 → 其他车辆的处理延迟变长。
- 防线现状：入站报文按设计文档 6.4 **刻意不限流**（依赖入站队列容量兜底，丢最旧）——
  该兜底**会连带丢掉正常车辆的数据**，因此本场景的真正解法是扩容消费线程或排查异常车端
  （见前置信号），F-01 修复接入的是企业侧 HTTP 维度，对此场景无直接缓解。
- 前置信号：`inboundQueueSize` / `inboundDropped` 持续增长，`mqttInboundQueue` 在大屏上不再归零。

**场景 3：数据库连接池成为并发瓶颈（虚拟线程启用后）**
- 触发条件：突发大量并发请求（如多个客户端同时首次加载大屏、或缓存集体过期瞬间）。
- 表现：HikariCP 20 个连接被占满 → 后续请求等待 → 超过 `connection-timeout: 3000` 抛异常 → 用户看到 500。
- 为什么在虚拟线程启用后概率提高：Tomcat 不再限制并发数（见 7.1），请求会全部涌到连接池。
- 前置信号：`hikaricp_connections_pending`（Actuator 已暴露 `prometheus` 端点）持续 > 0。

### 8.4 扩容路径

| 阶段 | 车辆规模 | 需要的动作 |
|---|---|---|
| 试点 | ≤ 50 台 | 当前配置即可（单实例、MySQL 单库）|
| 小规模 | 50~300 台 | ~~①修复 F-01~~（✅ 已完成）；②按磁盘反推 `track-point-days`；③开启 Redis（L2 缓存 + 跨实例去重）|
| 中等 | 300~1000 台 | ①多实例（定时任务分布式锁已具备——原 P-01 已修复，启用 Redis 即互斥）；②MySQL 主从读写分离；③`telemetryBuffered` / `inboundQueueSize` 配告警 |
| 大规模 | > 1000 台 | ①轨迹迁时序库（TDengine/InfluxDB）；②按区域分库；③媒体走对象存储 + CDN |

## 10 压测工具的缺陷修复记录

> **这一章存在的理由**：本轮的 3 个数据集全部由自研脚本产生。一个会"安静地给出漂亮数字"的脚本比一个跑不起来的脚本危险得多——后者会被立刻发现，前者会被写进报告当成结论。以下 5 项都是本轮实际遇到并修复的，**其中前 4 项在修复前会让数据完全失真，且不会产生任何报错**。

### 10.1 F-T01：鉴权头写错（Bearer vs X-Token）

| 项 | 内容 |
|---|---|
| 位置 | `load_test.py::fetch_json` |
| 原代码 | `request.add_header("Authorization", "Bearer " + token)` |
| 问题 | 平台的 `AdminTokenInterceptor` **只读 `X-Token` 头**，不认 Bearer 前缀 |
| 后果 | 每次请求都返回业务码 `2001`。而**鉴权失败的路径比正常查询更快**（拦截器直接返回，不进业务层），压测结果会呈现"QPS 极高、耗时极低"——与"性能优秀"的表象完全一致 |
| 修复 | 统一使用 `X-Token` |

### 10.2 F-T02：`TOKEN_HEADER` 常量未定义

| 项 | 内容 |
|---|---|
| 位置 | `load_test.py` 模块级常量 |
| 问题 | `http_get()` 里使用了 `TOKEN_HEADER`，但文件里只定义了 `TOKEN_BEARER_PREFIX` |
| 后果 | 带 `--token` 运行时立即 `NameError`。**这条路径只在"手动传入令牌"时被触发**，不带令牌运行完全正常——属于"只在一条分支上暴露"的缺陷 |
| 修复 | 定义 `TOKEN_HEADER = "X-Token"` 并删除误导性的 `TOKEN_BEARER_PREFIX` |

### 10.3 F-T03：`login()` 函数未实现

| 项 | 内容 |
|---|---|
| 位置 | `load_test.py::main` 调用了 `login()`，但**函数体不存在** |
| 后果 | 用 `--username/--password` 自动登录时 `NameError`。与 F-T02 互为镜像：一个坏在"手动传令牌"，一个坏在"自动登录"，**两条路径各自有一个坑** |
| 修复 | 实现 `login()`（POST `/api/v1/auth/login`，解析 `data.token`）|

### 10.4 F-T04：收尾读数用错了令牌变量

| 项 | 内容 |
|---|---|
| 位置 | `load_test.py::main` 末行 `print_cache_metrics(args.base_url, args.token)` |
| 问题 | 应为登录后得到的 `token`。用 `--username` 登录时 `args.token` 恒为 `None` |
| 后果 | **恰好把"压测跑完后最需要看的那份缓存命中率"变成一行 `2001` 失败提示**（本轮实测中被抓到：第一次采集时收尾的缓存指标为空）。压测本身仍有数据，所以很容易被忽略 |
| 修复 | 改为 `print_cache_metrics(args.base_url, token)` |

### 10.5 F-T05：并发参数在接口数较少时失效（口径问题，未修）

| 项 | 内容 |
|---|---|
| 位置 | `load_test.py::run_round` |
| 问题 | 实现为"每接口 1 个 worker"，提交的任务数 = 接口数 = 6，`max_workers=13` 的余量用不上 |
| 实测影响 | **实际并发 = 6，而不是参数写的 13。** 本文所有数据均按"实际并发 6"理解（口径 2）|
| 现状 | **本轮未修改**（改了会导致数据口径与已采集的三组数据不一致）。已在文档中显式标注口径，下一版脚本将按 `并发数 ÷ 接口数` 拆分 worker，使并发参数真正生效 |

### 10.6 为什么这类缺陷比"压测跑不起来"危险

五个缺陷有一个共同特征：**它们不产生错误，只产生偏差。**

| 缺陷 | 表面现象 | 真实情况 |
|---|---|---|
| F-T01 | QPS 极高、耗时极低 | 全部请求被鉴权拦截，压根没测到业务 |
| F-T02/F-T03 | 只有某一条使用路径报错 | 换一种用法就"正常"，缺陷被掩盖 |
| F-T04 | 压测数据看起来完整 | 唯一能证明缓存生效的那项指标是空的 |
| F-T05 | 报告写着"并发 13" | 实际并发 6，压力被低估一半以上 |

**因此本节的三条方法论**（已固化进脚本注释，供后续压测复用）：

1. **先验证测量工具本身**：压测前先确认"业务码是不是 0000"，而不是只看 HTTP 200。本次 DS-3 的探针脚本专门做了这件事——它把"鉴权失败"单独计数，因为鉴权失败会让"没有限流"这个结论变得不可靠。
2. **每个新脚本都要跑一次"已知会失败"的用例**：例如故意用错误口令跑一次，确认脚本会报错而不是给出漂亮数据。
3. **报告里必须能追溯原始输出**：本文所有数字都对应 `perf/*.txt` 中的原始日志，任何数字都可以被独立复核。
