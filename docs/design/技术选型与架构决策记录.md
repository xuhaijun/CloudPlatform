## ADR-001 Java 21 + 虚拟线程

- **背景**：接入层是典型的「大量阻塞 I/O」（MQTT 消费、HTTP 出网、JDBC），
  传统平台线程池模型下要么线程开太多（内存/调度开销），要么吞吐受限。
- **候选**：Java 21（虚拟线程）/ Go（goroutine）/ Node.js（事件循环）。
- **决策**：Java 21，`spring.threads.virtual.enabled=true`。
- **理由**：
  1. 团队 Java 工程资产与招聘面最厚；Go 版生态（车联网协议栈）需重造；
  2. 虚拟线程以**同步写法获得异步吞吐**，不用把全链路改成响应式（WebFlux 的
     调试与排障成本对运维型小团队过重）；
  3. JDBC 阻塞调用在虚拟线程下自动让渡（Go/Node 反而要绕）。
- **代价**： pinned 事件需监控（已把 pinning 事件打到 stdout，见详细设计 2）；
  虚拟线程不能池化，代码里禁止 `Executors.newVirtualThreadPerTaskExecutor()` 之外的用法。
- **状态**：✅ 已采纳。A/B 验证方法见《性能优化与压测报告》。

## ADR-002 Spring Boot 3.5 + JPA/Hibernate

- **背景**：需要 ORM、事务、调度、校验、Actuator 一站式；团队熟悉 Spring。
- **决策**：Spring Boot 3.5.16 + Spring Data JPA。
- **理由**：监管对接类项目**生命周期长、需求变更频繁**，JPA 的领域模型表达力
  与 Schema 演进工具链（`SchemaDdlGeneratorTest` 基线比对）优于裸 SQL/MyBatis；
  `ddl-auto=validate` 让「实体与库不一致」在生产启动期就炸出来，而不是运行期。
- **代价**：复杂查询需原生 SQL（轨迹抽稀、分批删除用 native query 解决）；
  Hibernate 6 的 `Instant` 序列化默认秒级，与 13 位毫秒契约冲突（已踩坑并统一为 long millis）。
- **状态**：✅ 已采纳。

## ADR-003 MySQL 8（生产）+ H2（本地/测试）

- **背景**：生产选型受客户环境约束（多数已备 MySQL）；开发与 CI 需要零依赖。
- **决策**：双轨——生产 MySQL 8.0.17+（分区增强手写 DDL）；H2 文件库跑测试与 local profile。
- **理由**：227 用例全量跑 H2，CI 不需要任何容器；`SchemaDdlGeneratorTest`
  生成基线与手写 DDL diff，保证 H2/MySQL 两套 Schema 不漂移；
  **生产 `ddl-auto=validate` + 真实启动验证**是两套库一致性的最后防线
  （`mvn test` 完全不校验 MySQL DDL，见工作流约定）。
- **代价**：MySQL 方言特性（分区、`ALGORITHM=INPLACE` 加索引）无法在单测覆盖；
  validate 不校验索引，需人工「仓储方法 ↔ 索引」对照。
- **状态**：✅ 已采纳。

## ADR-004 二级缓存：Caffeine L1 + Redis L2（可选）

- **背景**：总览/看板类接口读多写少，DB 直查在压测中是第一瓶颈。
- **决策**：自建二级缓存管理器；L1 进程内 Caffeine（TTL 5s），
  L2 Redis 仅在 `dssad.redis.enabled=true` 时启用（多实例共享）。
- **理由**：单实例部署（多数客户起点）不应该被强制装 Redis；
  TTL 5s 与前端 10s 轮询对齐（轮询间隔 < 缓存 TTL 只会打穿缓存）。
- **代价**：L1 失效靠 TTL，无主动广播；多实例下最多容忍 TTL 窗口内的轻微不一致。
- **实测**：DS-2 对照实验有正收益数据（见性能报告 4）。
- **状态**：✅ 已采纳。

## ADR-005 MQTT：Eclipse Paho 3.1.1

- **背景**：上游协议钉死 MQTT 3.1.1（`clean_session=false`），客户端无选型自由度，
  只有「用哪个库」的自由。
- **决策**：Eclipse Paho + 自建消费线程池（`consumerThreads=4`）隔离回调线程。
- **理由**：Paho 是 3.1.1 事实标准；自建消费队列使「入站处理」与「网络回调」解耦，
  回调里做重活导致的 ACK 超时被彻底规避。
- **代价**：Paho 的重连语义偏弱，自建指数退避（2s→60s）补齐（详细设计 3）。
- **状态**：✅ 已采纳。

## ADR-006 前端：Vue 3 + Vite 6 + Element Plus

- **决策**：Vue 3 `<script setup>` + TS strict + Pinia + ECharts 5 + Element Plus 2.9。
- **理由**：控制台类应用 Element Plus 组件密度最合身；Vite 开发期 HMR 与
  代理规则让前端零 CORS；构建期手动分包（vue/element/echarts 三 vendor chunk），
  路由级懒加载，首屏只拉登录页所需代码。
- **代价**：Element Plus + ECharts 合计 gzip 后仍 ≈ 686KB（首登后首次进总览需加载），
  由 Nginx gzip + 一年 immutable 缓存摊平；视图层无单测（P-09 已登记）。
- **状态**：✅ 已采纳（2026-09 补充：Nginx 静态资源 gzip 从关闭改为开启）。

## ADR-007 媒体存储：local / minio 双模

- **决策**：`dssad.storage.type=local|minio`，本地落盘默认，MinIO 生产可选。
- **理由**：取证视频单文件 ≤ 200MB，小体量客户先用本地盘 + Nginx 直出
  （`/media/` 不经应用层，GB 级流量不占 Tomcat 线程）；规模化后切 MinIO 不改代码。
- **代价**：local 模式无副本，依赖主机备份（`backup.sh` 只管 DB，
  媒体目录需另行 rsync —— 已在运维手册登记）。
- **状态**：✅ 已采纳。

## ADR-008 限流：自研滑动窗口计数器

- **候选**：Bucket4j / Resilience4j / 自研。
- **决策**：自研滑动窗口（`RateLimiter`），按 scope 分桶，`LongAdder` 计数零锁。
- **理由**：上游协议的限流口径是「单车辆」（MQTT 10 条/秒·车、HTTP 100 次/分·车），
  通用库的 key 语义要绕才能对上；自研 200 行换来完全可控 + 监控计数直达
  （`httpRejectedTotal` 等直接暴露到监控端点）。
- **代价**：实例级计数（多实例下阈值按实例数放大）——协议口径本就是「每车」而非全局，
  可接受；单测钉死计数分桶语义。
- **状态**：✅ 已采纳（F-01/P-03 均已接线并有行为断言）。

## ADR-009 部署双轨：容器 / jar+systemd

- **决策**：`docker-compose.prod.yml`（Nginx 唯一入口）与 jar + systemd + Nginx
  两套等价资产随仓库交付。
- **理由**：客户机房约束不可控（有 Docker 的用编排，无 Docker 的 systemd）；
  两套共用同一份 `.env.example` 与 Nginx 站点配置，避免配置漂移。
- **代价**：两套环境都要验证（部署说明 6「本地生产态验证」正是为此存在）。
- **状态**：✅ 已采纳。
