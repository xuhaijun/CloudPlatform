0.2 指标口径（读数字前必看）#

口径 1：用例总数以 surefire 的执行计数为准，不以源码里的 @Test 数量为准。

源码里 @Test 共 173 处、@ParameterizedTest 共 5 处，实际执行 200 个用例。 差额来自 @ParameterizedTest 的多组参数：同一段代码被多组输入各跑一次，就是多个用例 （本次新增的 ActuatorAccessControlTest 里，单个 @ParameterizedTest 就展开出 9 个用例）。 因此「200」才是防线宽度。

口径 2：「跳过 1 个」是刻意设计，不是遗漏。

跳过的唯一用例是 SchemaDdlGeneratorTest，它用 @EnabledIfSystemProperty(named = "ddl.gen", matches = "true") 关闭 —— 它是一个代码生成工具（从 Hibernate 元数据导出建表脚本），不是功能测试， 默认执行会覆盖 db/schema-mysql.sql，污染日常构建。详见 T-03。

口径 3：覆盖率门槛是 0.60，实测 0.73 —— 看的是「有没有下滑」，不是「是否达标」。

门槛的作用是拦住断崖式下滑，不是逼着把数字刷到某个值。 真正需要关注的是第 4 章的「未覆盖清单」和第 4.3 节的分支覆盖（50.55%）。

口径 4：Skipped 与 Disabled 必须能解释来源。

任何一个「跳过」都要能说清「为什么跳、什么条件下会跑」。说不清的跳过等于删除测试。

1 测试策略#

1.1 分层的理由#

测试分层不是为了「看起来规范」，而是因为不同层次的测试能发现的问题类型完全不同。 本项目按「能被哪一层发现」来设计分层：

层次 数量 能发现的问题 发现不了的问题
① 字典 / 常量契约 3 类 / 48 用例 协议字面量被改、码表被增删 逻辑错误、装配错误
② 纯逻辑单元 5 类 / 59 用例 算法错、边界条件错、编解码错、健康判定错 装配错误、SQL 错误
③ 安全契约 4 类 / 67 用例 签名算错、防重放被削弱、令牌可伪造、Actuator 可被越权访问 业务逻辑错
④ 装配集成 2 类 / 7 用例 @Cacheable 失效、native SQL 语法错、事务边界错 端到端链路断点
⑤ 端到端 1 类 / 18 用例 Handler 未注册、DTO 字段名不符、事务里写外部看不到 环境与部署问题
⑥ 环境与部署 0（脚本） 环境缺失、配置漂移、库表与实体不一致 见《开发与部署说明》的 14 条断言
⑦ 手工 / 需真实环境 0 真实 Broker 链路、容器、TLS、浏览器渲染 —（见第 8 章）

表中「类」为一个测试类整体归入某层（少数类横跨安全与契约，按主要保护目标归类）； 用例数按 surefire 实际执行计数。合计 16 类 / 200 用例，与第 2 章明细一致。

注意 ③ 安全契约一层已占全部用例的 1/3（67/200）—— 这是刻意的：本项目最贵的故障 不是「功能算错」，而是「该拦的没拦住」（令牌可伪造、签名可重放、Actuator 可越权读）。

1.2 三条设计原则#

原则一：能被 E2E 发现的，不重复写在单元层。 例如「同一 msgId 重发不产生重复轨迹点」只在 E2E 里断言一次（需要仓储与去重表一起工作）， 单元层不写「mock 仓储返回已存在 → 断言不插入」这种只能证明 mock 按自己期望工作的用例。

原则二：期望值用独立实现计算，不抄生产实现的常量。

// ✅ 正确：测试内用 JDK 原生 MessageDigest 独立算一遍
String expected = sha256(clientId + "CMAT");
assertEquals(expected, signer.deriveSecret(clientId));

// ❌ 错误：把实现里的常量复制过来
assertEquals("a3f5...", signer.deriveSecret(clientId));   // 实现算错，测试照抄 → 校验意义为零

这条规则写在 SecurityAndRateLimitTest 与 EnterpriseSignatureFilterTest 的类注释里。 EnterpriseSignatureFilterTest 甚至手写 SHA-256/HMAC，不复用 RegulatorySigner 的实现 —— 否则签名过滤器与签名器一起改错时，测试仍会通过。

原则三：把「文档里的枚举」钉死在代码里。 MqttTypeAndAckCodeTest、FaultCodeDictionaryTest、EnterpriseApiControllerTest 的断言对象是 接口文档的字段名、枚举值、错误码，而不是 Java 类。 理由：这些字面量一旦上线就不可改 —— 车端按 Topic 字面量订阅、监管平台按字段名硬编码解析。 改坏了代码不会编译失败，只会静默断链。

1.3 不做什么#

  • 不追覆盖率数字。目标是「关键路径与失败分支有断言」，不是「每个 getter 都被覆盖」。
  • 不为 mock 写测试。凡是「断言 mock 返回自己设定的值」的用例一律不加。
  • 不依赖真实时间。需要跨窗口/超时的用例注入可控时钟（见 3.4）。
  • 不在单测里连外部服务。监管平台地址刻意指向不可达端口，把「失败分支」变成确定性的可测路径。

新增两类的定位（本次随缺陷修复补上）：

3 逐类详述#

3.1 TopicParserAndBuilderTest（23 用例 / 3 组）#

保护目标：管道里最危险的一类故障 —— 消息静默丢失。

Topic 是 MQTT 的寻址层。它写错时不会有任何报错：消息被 Broker 收下， 只是没有任何订阅方匹配，于是凭空消失。生产上的表现是「某些车的某些数据永远不来」， 排查一次要数小时。

分组 覆盖内容
解析（Parser） 5 段正文下行 + 6 段附录 B（带版本号）下行的解析
构造（Builder） 上行/下行 Topic 的拼装，含企业 ID、车型、VIN 的占位规则
往返一致性 「构造 → 解析」必须还原出相同语义（锁死读写对称性）

为什么把附录 B 的 Topic 也测了：正文只用到 5 段，但附录 B 定义了 11 段（含版本号变体）。 只测用到的那 5 段，等于把「将来要用的 6 段」的正确性押在「以后再说」上。

3.2 MqttTypeAndAckCodeTest（19 用例）#

保护目标：报文类型与 ACK 标志的字面量。

断言的是文档里的数字，不是 Java 枚举名。例如 mqttType=14、res=1 表示成功受理。 这类字面量一旦上线即冻结（车端与监管平台按它订阅与判断）， 因此严格程度高于普通业务测试：增删一个类型必须是有意识的行为， 并同步更新用例 —— 否则测试失败会强制你停下来确认。

3.3 FaultCodeDictionaryTest（6 用例）#

保护目标：故障码字典（接口文档附录 A.1）。

字典是告警、统计、报表三处的公共维度。码值写错的表现既不像错误也难以察觉： 前端会显示成「未知故障码(4356)」这类既不报错、也没人会去追查的样子。

用例把码值集合整体钉死 —— 增删码值必须同步更新用例，杜绝「悄悄少了一个码」。

3.4 SlidingWindowRateLimiterTest（5 用例）+ SecurityAndRateLimitTest 的限流分组#

保护目标：限流算法的正确性，尤其是窗口边界。

本项目的限流实现是双窗口加权（sliding window counter）：

bucket       = now / W
elapsedRatio = (now % W) / W
estimated    = previousCount × (1 − elapsedRatio) + currentCount
allow ⟺ estimated < limit

之所以不用最简单的固定窗口：固定窗口在边界处会出现「前半窗末尾 + 后半窗开头」 各打满一次 → 瞬时最高可达 2 倍阈值，文档承诺的「100 次/分钟」会被突破到 200 次。

测试的关键设计：不依赖真实时间。

// ❌ 反例：Thread.sleep(1000) 等窗口过去
//    在 CI 上必然抖动 —— 进程被调度暂停 200ms 就会得到不同结论
// ✅ 正解：给 StateStore 注入可控时钟，跨窗口能精确地「一步跨过去」

窗口边界的正确性体现在「跨窗前后的几毫秒」，用真实时钟测等于把结论交给调度器。 因此本类给 StateStore 注入可控时钟，每次跨窗都精确可控、100% 确定性。

⚠️ 但这两组用例都只证明了「限流器算得对」，没有证明「限流器被调用过」。 这正是 F-01 能潜伏的原因，见第 9 章 T-02。

3.5 SecurityAndRateLimitTest（11 用例 / 3 组）#

分组 覆盖内容
RegulatorySigner：密钥派生与 HMAC secret = SHA256(clientId + "CMAT") 的派生与签名
RateLimiter：固定窗口限流（文档 9.1） 阈值判定、拒绝不计入计数、存储异常时放行（降级）
TokenService：平台访问令牌 签发、校验、注销；UUID v4 不可猜测

降级方向是要测的：限流存储异常时宁可放行也不误杀，这个方向必须被断言钉住 —— 否则某次「优化」把它改成 fail-closed，结果会是「Redis 抖动 → 全部车辆被限流」。

3.6 EnterpriseSignatureFilterTest（10 用例）#

保护目标：对外开放接口的防重放能力。

接口文档 6.3.1 把认证方式留给各企业自定，意味着没有任何外部规范兜底。 一旦这里的防重放逻辑被改坏（去掉 nonce 去重、放宽时间窗）， 后果是这个开放接口可以被任意重放调用，而且不会有任何编译期报错。

因此把每条安全约束都写成可执行断言：签名缺失 / 签名错 / 时间戳超窗 / nonce 重放 / 正常放行。 测试手写 SHA-256 与 HMAC 独立计算签名，不复用生产实现。

3.7 TwoLevelCacheTest（10 用例 / 3 组）#

保护目标：两级缓存的编解码与降级语义。

分组 覆盖内容
读路径 L1 命中 → 不走 L2；L1 未命中 → 查 L2 并回填 L1
L2 编解码 对象 → JSON → 对象 的类型能否还原（含 Instant / LocalDate / 泛型容器）
降级与语义 L2 不可用时的行为、脏数据（反序列化失败）必须安全丢弃而不是抛异常

为什么用 Mockito 假造 Redis 而不是起真 Redis：本类要验证的是编解码与降级逻辑 （哪一级命中、类型能否还原、脏数据是否安全），这些与 Redis 本身无关。 用假实现可以 100% 确定性地断言调用次数（「L1 命中时 L2 必须零调用」）， 起真 Redis 反而引入不确定性且拖慢 18 秒 → 数分钟。

3.8 CommonUtilsTest（19 用例 / 4 组）#

保护目标：四个「被全平台高频复用、出错后果隐蔽」的基础设施。

工具 出错的后果

3.9 MqttReliabilityTest（17 用例 / 3 组）#

保护目标：MQTT QoS 之上的可靠性补丁。

QoS 1 只保证报文到达 Broker，不保证对端业务处理成功。文档 5.1.4.1 / 8.1 要求： 对端未确认或明确报错时必须重发。因此这组用例直接对应监管考核项：

3.10 DashboardCacheIntegrationTest（3 用例）★ 装配类#

保护目标：@Cacheable 是否真的生效。

这组测试存在的唯一理由是：@Cacheable 失效有整整三类「代码看起来完全正确」的原因。

  1. 忘了 @EnableCaching → 注解被静默忽略，无任何日志；
  2. 同类内部方法自调用 → 绕过代理，注解形同不存在；
  3. CacheManager 没被装配成自研实现 → 退化成 NoOpCacheManager，命中率恒为 0。

这三种都不报错、不影响功能、单测全绿 —— 只是缓存完全没用， 而性能报告里 dashboardOverview 99.86% 的命中率会被无声地归零。 因此本类必须启动真实 Spring 上下文，断言缓存统计确实在增长。

与 TwoLevelCacheTest 的分工：那个测「缓存组件对不对」，这个测「缓存装上了没有」。

3.11 TelemetryRetentionServiceTest（4 用例）★ 装配类#

保护目标：每天 03:30 执行一次的 native SQL 清理语句。

为什么必须是集成测试而不是 Mockito 单测：

delete from t_vehicle_track_point where ts < ? limit 2000

LIMIT 在 JPQL 里根本不存在，只能走 native SQL。把仓储 mock 掉的写法能轻松通过， 却完全无法证明这条 SQL 在真实数据库上语法正确。而它只在每天 03:30 执行一次， 写错的代价是「清理任务静默失败数周后磁盘告警」。

因此在 H2（MODE=MySQL）上真跑一遍，同时覆盖： ① SQL 语法；② @Modifying + @Transactional 的事务边界； ③ 分批循环与安全阀（MAX_BATCHES_PER_RUN）；④ retention-days=0 时必须不清理。

3.12 PlatformEndToEndTest（18 用例 / 8 组）★ 端到端#

保护目标：装配错误与链路断点。 这是全套测试里最有价值的一层。

为什么必须有这一层：单元测试把每个类单独钉死后，仍然会漏掉「装配错误」—— Handler 没注册到路由表、Repository 查询方法名写错（启动期才报错）、 事务边界不对导致落库后查不到、DTO 字段名与报文体不一致导致静默取到 null。 这类问题只有把整条链路跑起来才会暴露。

链路：报文注入 → 业务处理 → 落库 → HTTP 查询。

# 分组 代表性断言
1 车端低频基础信息（5.1.4.3.2） 1Hz 位置上报后：车辆自动建档、当前位置可查、轨迹可回放
2 同一 msgId 重发不产生重复轨迹点（幂等去重）
3 准静态参数与低频状态（5.1.4.2.1 / 5.1.4.3.1） inh 上报后进入变更历史；low-state 上报后可从状态接口读到

为什么不用真实 Broker：模拟器接口内部直接调用生产的 MqttMessageRouter， 即报文走的是「解析 → 校验 → 去重 → 业务 → ACK → 留痕」同一条生产链路， 只是跳过了网络传输。这样既覆盖了全部业务逻辑，又让测试在无 Broker 的机器上能跑。 真正没有覆盖到的是「Broker 与 Paho 客户端」这一段，见第 8 章。

第 5、6 组的两条断言值得特别注意 —— 它们防的是越权与误判，属于安全属性： 「重复上传同一方向不被误判为收齐」防的是「用一段视频冒充四路」； 「ackMsgId 不匹配拒绝建档」防的是「任意 VIN 都能往别人事故里塞视频」。

5 覆盖率门槛#

5.1 本次发现并修复：门槛曾是死配置（T-01 / 交叉引用 E-03）#

pom.xml 声明了 jacoco.line.coverage.min=0.60，但只有 prepare-agent 与 report 两个执行， 没有 check —— 也就是说：

  • 属性被声明了，但没有任何东西引用它；
  • 覆盖率即便掉到 10%，mvn package 依然成功；
  • 报告会生成，看起来「有做覆盖率」，但它不拦任何东西。

这与《性能优化与压测报告》的 F-01（限流器未接入请求链路）属于同一族问题： 配置/代码存在，但从未被调用。

5.2 修复方案（已实施并验证）#

<execution>
  <id>check-coverage</id>
  <phase>verify</phase>
  <goals><goal>check</goal></goals>
  <configuration>
    <rules><rule><element>BUNDLE</element><limits><limit>
      <counter>LINE</counter><value>COVEREDRATIO</value>
      <minimum>${jacoco.line.coverage.min}</minimum>
    </limit></limits></rule></rules>
  </configuration>
</execution>

实测（mvn verify）：

  → Analyzed bundle 'dssad-cloud-platform' with 167 classes
All coverage checks have been met.
BUILD SUCCESS (33.308 s)

5.3 门槛策略#

命令 出报告 校验门槛 定位
mvn test 是 否 本地快速迭代
mvn package 是 否 只想出包
mvn verify 是 是 CI 与发布（scripts/build.sh 默认走这条）

为什么是 0.60 而不是把当前值 0.73 设成门槛：门槛的作用是拦住断崖式下滑， 不是逼所有人绕过它。留 13 个百分点缓冲，可以让「新增一个纯 DTO 类」不至于直接打断构建； 若设成 0.73，第一次加个未覆盖的 DTO 就会逼着开发去写无意义的 getter 测试 —— 那是负收益。

6 测试隔离与「幽灵用例」防治#

「幽灵用例」指单独跑通过、全量跑随机失败的用例。它是最消耗团队信任的一类问题 —— 一旦出现，人们就开始习惯性重跑 CI，测试的实际保护力归零。本项目从三个方向防治：

6.1 数据隔离#

spring:
  datasource:
    url: jdbc:h2:mem:dssad_test;MODE=MySQL;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE
  jpa:
    hibernate:
      ddl-auto: create-drop        # 上下文销毁即清表
  • 内存库 + create-drop：每个 Spring 上下文都是全新的库，不存在跨用例残留。
  • MODE=MySQL：让 H2 用 MySQL 方言解析 SQL。 这一点很关键 —— TelemetryRetentionServiceTest 要真跑 delete ... limit ? 这条 native SQL，若方言不对会给出假绿的语法校验。

6.2 缓存必须彻底关闭（★ 最容易踩的一条）#

spring:
  cache:
    type: none
dssad:
  cache:
    enabled: false

为什么必须两处都关：单测若留着缓存，会出现这样的时序：

A 用例注入报文 → 统计接口算一次 → 结果进缓存； B 用例再注入报文 → 统计接口从缓存读到 A 时刻的旧值 → 断言失败。

失败信息通常表现为「计数少了一个」，看起来像业务 bug，实际是缓存串了用例。 而且它会随机复现（取决于用例执行顺序），是最典型的幽灵用例来源。

缓存行为本身由 TwoLevelCacheTest（直接 new TwoLevelCache(...)）与 DashboardCacheIntegrationTest（显式构造上下文）覆盖， 不需要在业务集成测试里掺进来。这是「用专门的测试测专门的东西」的实例。

6.3 定时任务必须关闭#

dssad:
  retention:
    # 单测关闭自动清理：定时任务在测试上下文里跑起来会删掉其他用例插入的数据

保留策略清理（每天 03:30）若在测试里被触发，会删除其他用例刚写入的行， 造成「随机少数据」。清理逻辑本身由 TelemetryRetentionServiceTest 显式调用来验证， 既可控又不影响他人。

6.4 时间必须可控#

凡是涉及窗口/超时的用例（SlidingWindowRateLimiterTest、MqttReliabilityTest 的重发间隔）， 一律注入可控时钟而不是 Thread.sleep：

固定窗口与滑动窗口的核心差异体现在「窗口边界前后几毫秒」的行为上。 依赖真实时钟的测试在 CI 上必然抖动 —— 进程被调度暂停 200 ms 就会得到不同结论。

6.5 外部依赖必须指向「确定不可达」的地址#

dssad:
  regulatory:
    base-url: http://127.0.0.1:9/regulatory   # 端口 9（discard），必然失败
    timeout-millis: 500
    retry-delays-millis: 10,20                # 把重试间隔压到毫秒级

把「对端不可达」变成一条确定性的可测路径：既覆盖了降级分支， 又不会因为真去连一个不存在的域名而产生几秒超时或不可复现的网络错误。

  2. 「同一 VIN 心跳超时后 → online 必须变为 false」（保护在线状态）
  3. 「MQTT 断连时 → 至少有一处可被外部观测的信号为异常」（保护通道监控）

附录 B 断言口径约定#

写新用例时必须遵守，否则会得到「看起来在测、其实测错」的用例。

约定 说明
业务成败看业务码，不看 HTTP 状态码 平台在 HTTP 200 的响应体里用 code 表达失败（2001 未授权 / 3001 不存在 / 4001 限流）。鉴权失败路径比正常查询更快 —— 只看状态码会把「全部被拒」当成「性能极佳」
时间统一按 13 位毫秒时间戳断言 文档 1.4 约定所有 timestamp 为毫秒；Instant 序列化为 13 位数字，LocalDate 序列化为数组
期望值独立计算，不抄实现常量 见 1.2 原则二
不依赖真实时间 涉及窗口/超时的用例注入可控时钟
不为 mock 写测试 「断言 mock 返回自己设定的值」不构成验证
外部依赖指向确定不可达地址 把降级分支变成确定性可测路径（http://127.0.0.1:9/）
协议字面量必须逐条钉死 字段名、枚举值、错误码一旦上线不可改；改坏只静默断链
优先保证失败分支有断言 边界与异常路径出错概率远高于主流程
