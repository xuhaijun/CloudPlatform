### 关键工程决策（写进文档的设计理由）
- **主键三策略**：`vin` 业务主键 / 大表雪花 ID（IDENTITY 会关闭 JDBC 批量插入，吞吐差 5~10 倍）/
  小表自增。雪花时钟回拨 >5ms 直接抛异常（宁失败不写脏数据）。
- **时间字段三语义**：平台时间 `created_at(DATETIME(6))` / 业务时间 `reported_at` /
  轨迹 `ts(BIGINT)`（协议原生、支持 `mod(ts, bucket)` 降采样、整数范围比较更快）。
- **3 张追加型流水表不继承 BaseEntity**（轨迹/状态/留痕），每行省 16 B。
- **物理外键只有 1 条**（`t_fault_item.fault_record_id`）：流水表加外键会让高并发批量写入相互等待。
- **分批删除必须把 `@Transactional` 标在仓储方法上**（Spring Data 的 `@Modifying` 查询**不会**自动获得
  写事务，漏标抛 `TransactionRequiredException`）；标在服务层循环上会把几千批合并成一个巨型事务。
- **JPQL 无 `LIMIT`** → 删除用 native SQL；MySQL 的 `DELETE ... LIMIT` 与 `ORDER BY` 互斥。

### 本轮新发现 2 个高危缺陷（均已复核确认，登记为 P-01 / P-02）
- **P-01 多实例下定时任务重复执行**：`@Scheduled` 是进程级的，`scheduledPurge`（03:30 批量清理）
  与 `scheduledPull`（00:05 地图拉取）**无分布式锁** → 两实例同时跑 `DELETE ... LIMIT`
  会相互等待甚至死锁。建议 ShedLock 或 `SET NX PX` 锁。
- **P-02（高危）车辆上下线永远不刷新**：`VehicleService.markOfflineVehicles()` 已实现批量置离线
  （`markOfflineBefore` 一条 UPDATE 搞定），但**全项目无任何调用方、也没有 `@Scheduled`**
  → `online` 字段一旦置 true 永不回落，大屏「在线车辆数」持续偏高。
- 另有 P-03（入站报文无限流，仅靠队列容量兜底）、P-04（远驾配对靠「最近一条未结束」，
  协议无接管单号）、P-05（离线队列进程内，重启丢）、P-06（地图 area-code 用
  `System.getProperty` 而非配置项）等 10 项。

### 沉淀的工程判断（写进文档的技术理由）
- **6 类线程全景**：Tomcat 20~200 / Paho 回调 1 / 消费 4 虚拟 / 重连 1 / **`scheduling-1` 只有 1 个
  → 所有定时任务串行**（这就是 03:00 与 03:30 必须错开的真实原因）。
- **接 `Throwable` 而非 `Exception`**：消费循环里 OOM 等 Error 会直接杀死消费线程，
  4 个死 1 个 = 吞吐降 25% 而监控上看不出来。
- **`@Modifying` 必须配 `clearAutomatically=true`**：直接 UPDATE 绕过持久化上下文，
  不清一级缓存会让同事务内后续 `findById` 读到旧值。
- **温度偏移的双字段设计**：`temperature`（协议原文）+ `@JsonProperty("temperatureCelsius")`
  派生真值，**两者同时出现在 JSON 里**，从契约层消除漏减。
- **DP 抽稀的单位一致性坑**（代码里已有一条长注释）：纬度必须乘 111320 换成米，
  早期只把经度乘了 `scaleLng`、纬度拿「度」算，导致南北向偏移被缩小 11 万倍 →
  **直角弯被抽成直线，且只在南北向道路暴露**。
- **`ElapsedRatio` 全整数运算**避免浮点误差导致限流边界抖动；**被拒请求不计入计数**，
  否则「上一窗满额」时探测请求会把每个窗口填满 → 车辆被永久封死。
- 前端 **10s 轮询 > overview 5s 缓存 TTL**，否则用户看到的是缓存值却以为刷新生效。
- **多实例第三个必须项**：`dssad.instance.worker-id` 必须显式配置且各实例不同
  （雪花机器位默认按本机 IP 末段推导，容器环境下可能重复 → 主键冲突）。

### 关键工程结论（写进报告的技术理由）
- **本平台性能矛盾不在读侧而在写侧**：读侧 1180 req/s vs 实际需要约 40 req/s（余量 30 倍）；
  写侧 1000 车 1Hz = **8640 万行/天 ≈ 14.3 GB/天**，是物理量，只能用「批量写 + 保留期」解决。
- **批量写入把「每秒 1000 次事务」压成「每秒 1 次事务、2~5 次往返」**（降低 200~500 倍）。
- **缓存收益 -85% 是本机条件下的下界**：H2 内存库 + 1 行数据 + 并发 6，三个因素都低估缓存价值；
  收益与「回源成本」成正比。L2（Redis）本轮**完全未验证**（本地 redis.enabled=false）。
- **口径陷阱三条**：① 脚本 QPS 是**单接口**吞吐（×6 才是系统总吞吐）；
  ② `--concurrency 13` 实际并发只有 6（每接口 1 worker）；
  ③ 业务成败必须看业务码，鉴权失败比正常查询**更快**，会把"全被拒"看成"性能极佳"。
- **99.86% 命中率的正确读法**：6 轮总耗时 < 7 秒 < 本地 TTL 10 秒，所以每个缓存名只穿透 1 次；
  生产大屏（TTL 5~60s）实际会落在 70%~95%，**不能拿 99.86% 当生产预期**。
- **发布后要先打预热流量**：冷启动首个窗口内 P50 约为稳态的 1.5~2 倍（JIT+连接池+缓存三重预热）。
- **虚拟线程启用后 `max-threads` 不再是并发上限**，HikariCP 的 20 个连接成为唯一排队点，
  突发流量表现为"3 秒后大批 500"而非"排队等待" → 上线前须在预发验证并发 200。

### 压测工具缺陷 5 项（前 4 项会**静默**污染数据，已修）

### ⚠️ 最重要的架构结论（踩坑，勿改回）

**Spring Boot 的 `/actuator/health` 聚合端点始终包含所有已注册的 `HealthIndicator`，
health group 的 `include` 只能往里加，无法把某个指示器从聚合里摘出去**（官方文档 + 本机实测一致）。

第一版把通道做成 `HealthIndicator` 挂到 group `mqtt`，实测：

```
GET /actuator/health/mqtt → 503 DOWN
GET /actuator/health      → 503 DOWN   ← 副作用：把「依赖故障」升级成「实例不健康」
```

后果与设计意图正好相反：用 `/actuator/health` 判活的编排会摘流/重启应用，而 Broker 故障重启毫无用处。
**改走业务端点** `/api/v1/monitor/mqtt-health`：① 不动聚合端点；② 天然被 Nginx `/api/` 代理，
不需要为它在被 404 收敛的 `/actuator/` 上开洞；③ 与既有探针同源。
（该端点已在 `WebConfig` 加入 `excludePathPatterns`，与 health-check 一样免令牌。）

### 🕳 同一个坑踩了两次（必须固化）

为「可测性」给 Spring Bean 加**第二个构造器**（包级、收配置记录以便单测免造整个 AppProperties）时，
Spring 面对多个候选构造器**不会猜**，而是回落到无参构造器并报
`No default constructor found` —— 25 个 context 用例一起挂，且只在启动期暴露。
**修法：给生产构造器显式加 `@Autowired`**。本次在 `MqttChannelHealthIndicator`（已废弃的初版）
和 `MqttChannelProbe` 上各踩一次，两次都是同一个错误。
